文中的验证结论只在文档明确标注的范围内成立，未经验证的能力一律按 fail-closed 处理。

## 3. 逐层验证

### 第 1 层：进程与 IPC

1. 启动 `MentorRecorder.Desktop.exe`，确认它拉起了 `MentorRecorder.Collector.exe`。
2. 打开诊断页，确认握手成功（显示 Collector 版本与 `protocol_version = 1`）。
3. 用 `netstat -ano | findstr <两个进程的 PID>` 确认**没有任何 LISTENING 端口**，桌面端也没有出站连接。
   采集服务只在当前版本没有可用档案且共享校准开启时，才会短暂连向 GitHub 或 jsDelivr 的 443 端口
   （[privacy-boundary.md](privacy-boundary.md) §8.2）。若用户在「设置 → 播报」中选择了在线语音，
   播报时还会连向所选的语音服务（§8.3）。要验证完全不联网，应先在设置中关闭
   「游戏更新后获取其他玩家的共享校准」并把语音引擎改回本机语音，
   或设置 `MR_DISABLE_SHARED_FETCH=1` 与 `MR_DISABLE_ONLINE_SPEECH=1` 后重启本软件。
4. 用 Process Explorer 确认 Collector **没有打开游戏进程的句柄**。
5. 确认安装目录中**没有** `deucalion-*.dll`。

**任一条不符即为边界违规**：应立即停止验证，并先行修复。

1. 诊断页应显示 `npcap_installed = true` 与版本号。
2. `ListCaptureAdapters` 应列出网卡。记下游戏所在网卡的 `adapter_id`。
3. 若某张网卡被标记 `recommended`，确认它与游戏实际使用的网卡一致。

### 第 3 层：协议档案

1. 诊断页显示识别到的 `game_build`。
2. 国服 build `2026.08.05.0000.0000` 应识别为 `VERIFIED`（档案 `cn.2026.08.05`）。其他 build 的

3. 没有 `VERIFIED` 档案时不产生任何自动记录，这是预期行为。

> 若要继续向下验证，需要先按
> [protocol-profile-format.md](protocol-profile-format.md) §7 制作一份档案。
> 档案中只应填写在本机亲自观察且能复现的常量，并逐条填写 `evidence`。
> **不得**使用来源不明的 opcode 表。

> 若仅需确认 Npcap、适配器与计数链路可用，可临时将
> `capture.allow_without_profile` 设为 `true`，进入**仅诊断模式**：
> 允许抓包计数，但不解析字段、不自动写入记录。完成后应恢复默认值 `false`。

> 尚无任何档案时，第一步不是编写档案，而是**先行取证**，

## 3.5 第一次真机取证（`--capture-trace`）

这是从无档案状态获得第一份候选档案的唯一合规路径。
其产物是一份**脱敏的 opcode 级证据文件**，既不是档案，也不是记录。

### 3.5.1 记录范围

每条消息只写入下列各项：序号、相对毫秒、UTC 时间、方向（`S2C` / `C2S`）、
段类型、opcode、**负载长度**、以及**负载 SHA-256 的前 12 位**。

**不写入**：任何负载字节（十六进制、Base64 或其他任何写法）、
IP 与 MAC 地址（已经哈希过的连接键同样不写）、角色名、聊天内容、队友信息、网卡 GUID
（只写其 12 位指纹）。标记只接受下文列出的五个固定词，不写入自由文本。

该模式符合 [privacy-boundary.md](privacy-boundary.md) §5 对诊断模式的要求：
由用户显式开启、范围有界、有明确的保留策略、不含聊天内容、凭据与地址。三条边界均为具体数值：

- **行数**：消息行默认上限 20 万（`--max-lines` 可调），标记行上限 1 万；达到上限后只计数、
  不再写入，并在 summary 中标记 `truncated`。
- **时长**：`--duration-seconds <n>` 最大 86400；**省略或取 0 表示不限时长**，
  仅由行数上限、游戏退出或 Ctrl+C 终止。界面上的“开始验证”另有 **2 小时**的硬上限。
- **保留**：命令行通路写入用户自行指定的文件，本软件既不清理也不覆盖该文件。界面通路写入
  `<数据库目录>\traces\<时间戳>-<GUID>\`，只保留**最近 10 个**会话目录，且保留期不超过 **7 天**，
  在启动时与每次会话结束后各清理一次。

### 3.5.2 步骤

**第 1 步：安装 Npcap。**
由用户从官方站点自行安装，安装时**必须**勾选 "WinPcap API-compatible Mode"。
本软件不下载、不内置、也不分发该组件。

**第 2 步：自检。**

```powershell
MentorRecorder.Collector.exe --capture-doctor
```

`npcap.status` 必须为 `READY`，`游戏进程 running` 必须为 `True`，
且网卡列表中有一张被标记为 `[*]`（`游戏流量=True`）。
任一条不满足时应先行解决：取证模式会输出同一段文字并以退出码 1 终止。

**第 3 步：开始取证。**

```powershell
MentorRecorder.Collector.exe --capture-trace trace.jsonl
# 可选：--duration-seconds 1800   限时（0 或省略 = 直到 Ctrl+C 或游戏退出）
#       --adapter <id>            指定网卡（自检里那张 [*] 的 id）
#       --max-lines 200000        行数上限，默认 20 万行
```

该命令**不打开数据库、不建立命名管道、不解析任何字段**，只写入指定的文件。
若目标文件已存在，命令拒绝覆盖，因此每轮取证应使用新的文件名。

**本步必须从新的游戏 TCP 连接开始。** 若命令发现游戏已在所选适配器的本地地址上连接区服，
则直接拒绝启动：中途接入会使 Oodle 流状态不完整，短 trace 只会得到大量 `decode_errors`，
不能作为候选 opcode 证据。
所选适配器没有可绑定的 IPv4 地址时同样拒绝启动，此时应回到 `--capture-doctor` 选择带 IPv4
地址的实际流量网卡，不能由抓包源自行猜测。
推荐做法是先用 `--capture-doctor` 记下标记为 `[*]` 的网卡 `id`，在重新登录前运行
`--capture-trace --adapter <id>`，或在断线重连后立即启动。

**第 4 步：在游玩过程中打标记。**

程序会在窗口中提示：游戏内发生下列事件的**当下**，
在该窗口输入对应的词并回车。

| 输入的词 | 输入时机 |
|---|---|
| `queued` | 点击“开始排队”的时刻 |
| `pop` | 弹出确认框的时刻 |
| `entered` | 画面完成读条、进入副本的时刻 |
| `victory` | 出现通关结算的时刻 |
| `left` | 主动离开或被踢出副本的时刻 |

只有上述五个固定词会被记为标记，大小写不敏感，落盘统一为小写；其他输入被忽略。
**同一流程至少应完整进行两遍**：候选表的判据是“每一次都出现”，
只进行一遍时几乎所有 opcode 都满足该条件，候选表随之失去意义。

程序每 5 秒向标准错误输出一行状态，包含消息数、速率、解码错误、丢弃与标记数。

**第 5 步：以 Ctrl+C 结束。**
程序会补齐 summary 行、计算 SHA-256、写出 `trace.jsonl.sha256`，并在屏幕上输出该哈希。

**第 6 步：离线查看结果。**

```powershell
MentorRecorder.Collector.exe --trace-report trace.jsonl
MentorRecorder.Collector.exe --trace-report trace.jsonl --around pop --window-ms 3000
```

离线报告将消息索引保留在内存中，因此拒绝单个超过 64 MiB 或 25 万消息行的 trace。
更长的取证应在采集阶段拆分为多轮，而不是事后加载单个超大文件。

报告有四部分：总览、按方向的 opcode 直方图（条数 / 长度最小值 / 最大值 / 众数）、
每个标记前后 ±窗口内的消息明细、以及**候选表**。

### 3.5.3 候选表的判读

候选表只列出同时满足下列两条的 opcode：

1. 在**同名标记的每一次**窗口中都出现，即 `命中/次数` 为 `2/2`、`3/3` 一类；
2. 按“窗口内条数 / 全程条数”的比例排序，比例越高越靠前。

比例接近 1.00 表示该 opcode 几乎只在该标记附近出现，
这正是 `CONTENT_FINDER_POP` / `ZONE_INITIALIZATION` / `DUTY_RESULT` / `PLAYER_JOB`
一类消息应有的分布。比例很低（例如 0.05）的条目属于背景噪声，只是恰好同时出现。

**候选始终只是候选。** 一个数值要成为档案中的常量，必须同时满足：

1. 至少**两次相互独立的会话**（不同时间、且重启过游戏）都将其列为同一标记的候选首位；
2. 留存**脱敏固件**及其 **SHA-256**（见 [protocol-profile-format.md](protocol-profile-format.md) §5、§7）；
3. 在档案中写明对应的 `evidence` 条目，`method = "OBSERVED_LOCAL_TRAFFIC"` 并注明样本数。

仅满足其中两条时，档案的 `compatibility_status` 只能为 `CANDIDATE`，
解析器保持 fail-closed，不产生任何记录。

### 3.5.4 常见情况

| 现象 | 含义 | 处理 |
|---|---|---|
| 立刻退出 1，并先打印一份自检 | Npcap 不可用 / 游戏未运行 / 网卡无法确定 | 按自检输出的指引处理；网卡不确定时用 `--adapter` 显式指定 |
| 已开始，但 `消息 0` 且提示“抓包中断” | 监视器致命错误 | 查看 `%LOCALAPPDATA%\MentorRecorder\logs\` 中的 `monitor_trace` 行 |
| 日志中出现 `Cannot find one or more signatures in ffxiv_dx11` | 当前 Machina 版本的 Oodle 特征与该客户端版本不匹配，取不到解压函数 | 本项目无法在代码中绕过：需等待 Machina 更新特征，或按 `DEC-OODLE-01` 的选项 A 自备 `oo2net_9_win64.dll`（本项目不分发该文件） |
| 状态行始终为 `消息 0` 且没有报错 | 选择了错误的网卡（例如流量经 VPN 虚拟网卡） | 更换网卡后重试 |
| 结束时提示达到行数上限 | 已写满 `--max-lines` | 提高上限，或分多次采集，每次只覆盖一个流程 |

### 3.5.5 提交之前

trace 文件本身已脱敏，但**不应提交到 issue**：
它属于用户本机的证据。按 §6 的要求只提交**结论与 evidence 条目**，
必要时附上 SHA-256，而不是整份文件。
任何情况下都不要粘贴原始报文、角色名或其他玩家的信息。

## 4. 必须覆盖的场景

每个场景都需人工记录实际发生的过程，再与本软件的记录逐条比对。

| # | 场景 | 期望的 `result` | 期望的 `entered_at_utc` |
|---|---|---|---|
| 1 | 排到导随，正常完成副本，出现通关结算 | `COMPLETED` | 非空 |
| 2 | 排到导随，弹窗后不点击确认或点击取消 | `CANCELLED_BEFORE_ENTRY` | **空** |
| 3 | 进入副本后主动退出 | `LEFT_OR_ABANDONED` | 非空 |
| 4 | 进入副本后拔网线 / 断开网络 | `DISCONNECTED` | 非空 |
| 5 | 进入副本后强制结束游戏进程 | `INTERRUPTED` | 非空 |
| 6 | 副本进行中结束 Collector，随后重启本软件 | `INTERRUPTED`，且出现在“待复核”列表 | 非空 |
| 7 | 排到**非导随**的其他随机任务并完成 | **不产生任何记录** | — |
| 8 | 中途切换职业后再排 | `job_id` 正确 | 非空 |

场景 4 **可以实际复现**：对于已经投递过解码消息的游戏连接，Collector 在其收到 FIN/RST
或从系统连接表中消失时收尾为 `DISCONNECTED`（见 [state-machine.md](state-machine.md) §3.6）。
拔掉网线之后不要立即关闭游戏，也不要立即重新登录，否则结果会分别变为 `INTERRUPTED` 与
“换区收尾”，测试的就不是这条路径。

同时校验：

- `duration_ms` 与秒表实测相差应在数秒内，且**不为负**；
- `duty_name` 与实际副本一致；`content_id` 仅在报文确实携带该字段时非空，
  仅按区域识别出的记录 `content_id` 为空、`territory_id` 非空
  （本机数据库中 `duty_source = 'TERRITORY'`，见 [data-model.md](data-model.md) §1.4）；
- 终态不在“当前记录”中查看：收尾之后状态机立即回到空闲（[state-machine.md](state-machine.md) §3.13），
  应查看记录列表或监听 `run_finished`；
- 场景 6 的记录**不得**被自动判定为 `COMPLETED`；
- 场景 2 的记录**不计入** `attempt_count`（见 [statistics-definitions.md](statistics-definitions.md)）。

## 5. 统计与手工更正

1. 完成上述场景后，打开仪表盘，用人工统计的数字核对
   `attempt_count` / `completed_count` / `completion_rate` / `leave_rate`。
2. 确认 `DISCONNECTED` 与 `INTERRUPTED` 各自独立成行，**未**被计入离开率。
3. 对场景 6 的记录执行一次 `CorrectRun`（改为实际结果并填写理由），
   确认修订链新增一条、`revision` 递增 1、记录被标记为“已人工更正”。
4. 依次执行一次 `SoftDeleteRun` 与 `RestoreRun`，确认统计随之变化且历史完整。
5. 导出 CSV 与 JSON，确认包含 `source` / `manually_created` / `manually_corrected` / `revision`。
6. 执行一次 `BackupDatabase`，确认备份文件可被打开且完整性检查通过。

### 5.1 验证结果的记录方式

在 `protocol-profiles/<region>/` 下的档案中补充 `evidence` 条目
（`method = "USER_CONFIRMED"`），并在 PR 描述中写明：

- 区服（CN / GLOBAL）与游戏版本；
- Npcap 版本、网卡类型；
- 上表 8 个场景各自的实测结果，以及与本软件记录是否一致；
- 观察到的偏差与其可能原因。

**不要**在 issue 或 PR 中粘贴原始报文、角色名、好友名或任何其他玩家的信息。

只有在上述场景全部通过且证据被记录之后，才可以将
`LIVE_CAPTURE_STATUS` 从 `UNVERIFIED` 改为 `VERIFIED`，
并同步更新本文件、README 与发布说明。

| 项 | 结果 |

| 环境 | Windows 11，Npcap 1.88（WinPcap 兼容模式），游戏流量经 Meta Tunnel 网卡 |
| `--capture-doctor` | Npcap READY，进程识别 CN / build 正确，网卡自动识别正确 |

两条重要观察：

1. **Oodle TCP 解压是有状态的**：在连接建立之后才接入的抓包取不到字典训练数据，
   其后每一条报文都会解码为无效数据，表现为本软件的分帧层拒绝，而不是 Machina 报错。
2. **国服客户端在传送换区时不会新建区域连接**：本次传送前后端口完全相同，
   因此传送不能刷新连接状态，**必须在登录之前开始抓包**。
   登出到标题画面时游戏进程没有任何 TCP 连接，可在此时开始抓包，然后重新登录。

由此形成的产品要求（已实现）：

- `capture.follow_game` **默认开启**：Collector 每秒轮询游戏进程，进程出现后即自动开始抓包，
  时点远早于登录，用户无需记忆启动顺序。自动开始被拒绝时（无 Npcap、无档案或无网卡）
  在 30 秒后重试，而不是每秒重复报错。
- 常规抓包检测到“已有连接且解码全部失败”时，`CaptureStatus.midstream_suspected = true`，
  `hint` 明确提示“登出到标题画面再重新登录一次（不用关闭游戏）”，恢复后提示自动消失。
- 界面不再常驻“抓包必须在登录之前开始”的横幅，仅在自动跟随关闭时给出警告与一键开启入口。

**协议层仍为 UNVERIFIED**：本次未对任何 opcode 做判定，`LIVE_CAPTURE_STATUS` 未变更。

## 7. 被动验证流程

候选档案 `cn.2026.08.05.candidate` 只适用于国服 build `2026.08.05.0000.0000`，状态恒为
**CANDIDATE**，仅含假设条目。§6 的 Oodle 签名验证只证明解压链路，不证明 opcode 或字段。
正式档案 `cn.2026.08.05` 的当前状态见 §0。

### 7.1 用户：正常游玩，结束后核对

1. 在另一台电脑上克隆仓库并切换到 `main`，按 README 构建并启动桌面端与 Collector。
   打开“捕获诊断”，显式开启“候选档案验证”，该开关默认关闭。自 2026-09-07 起，候选验证与
   正式档案**并行**运行：开启后正式记录照常产生，观测数据另写入独立账本。
2. 需要维护者研究字段时，在“对照核对要保存的报文”中点击 **“选用推荐”**，其中含排本与弹窗
   两组，报文按用途以中文名列出，数据由 `CaptureStatus.candidate_hypotheses` 提供。默认不选中任何一项。
   十六进制编号只在“高级”中显示；未知报文、混淆报文以及声明上界超过 512 字节的报文会被拒绝，错误显示在卡片内。
   不需要研究负载时保持空白；“全部清除”在候选验证关闭时同样可用。
3. **先启动本软件，再启动游戏**。自动跟随默认开启，游戏进程出现后即自动开始候选捕获，
   登录前无需任何操作。若在游戏已登录之后才打开本软件，捕获页会提示登出到标题画面并重新登录一次，
   其间无需关闭游戏；传送不会重建国服的这条连接，不能代替重新登录。候选模式使用常规被动捕获链路，
   不需要独立“桌面验证取证”工具的手工标记。
4. 正常排入若干次随机任务，**其中至少一次为指导者任务**，完成后再切回本软件。
   游戏内无需热键、标记或其他额外操作。捕获页会显示匹配到的候选档案 id 与保留观测数；
   版本不匹配时不会猜用候选档案，也不会产生正式记录。
5. 结束后打开 **“对照核对”** 并刷新。页面按时间倒序列出本次捕获中发生的**事件**，
   每行一件事，而非每行一条报文：登录进入游戏、排本登记、取消排本、副本查找器通知
   （很可能是弹窗）、进入副本、离开副本、换区。推断规则见 §7.3。
   报文级明细位于页面底部的“报文明细（维护者用）”，默认折叠。
   若抓包仍在继续且索引发生变化，界面会提示刷新；完整索引建立之前不显示时间线。
6. 对照实际经历或 ACT 的战斗时间线，逐条选择 **对 / 错 / 不确定**，并可填写备注，
   例如任务名称、是否出现弹窗。无法确认时选择“不确定”。备注与结论只写入独立候选账本，不修改正式记录。
7. 点击 **“导出证据”**，复制界面显示的本地 JSON 路径，同目录下有 `.sha256` 边车文件。
   默认输出目录为 `%LOCALAPPDATA%\MentorRecorder\exports`，不会覆盖已有文件。
   文件头的 `contains_raw_payload` 与 `research_payload_opcodes` 反映本次导出的
   **实际保留数据**。关闭该模式或清空白名单不会删除此前保存的研究负载，导出结果仍可能包含原始正文。
   应通过用户自行选择的私密方式将 JSON 与 SHA-256 边车交给维护者，不要粘贴到公开的 issue 或 PR。
   本软件不会上传、联网发送或自动联系维护者。

观测最多保留 **20,000 条 / 30 天**，核对历史随所属观测一并清理，研究负载每条最多 512 字节。
实际负载超出上限时整段不保存，也不截取前缀；元数据仍按观测规则保留。
需要保留研究证据时应在过期前导出。详见 [隐私边界 §5.1](privacy-boundary.md)。
关闭候选验证会立即停止新候选写入；当前捕获不会自动转为正式解析，需要停止后重新开始。

### 7.2 维护者：离线推导与后续复现

1. 核对 JSON 的 SHA-256 与边车，确认档案 id、游戏版本、会话、核对备注与原始负载声明。
   无 `payload_hex` 的元数据观测不能用于推断字段。先使用基于 Python 3 标准库的工具生成稳定性报告：

   ```powershell
   python tools/candidate-evidence/derive_fields.py C:\evidence\candidate.json --output-dir C:\evidence\analysis-1
   ```

2. 结合用户核对结果，明确选择弹窗 hypothesis 与 roulette id 候选值。当前 `data/` 没有权威的
   roulette id 来源，须通过 `--roulette-id` 明确输入 1..65535 的十进制或十六进制值，
   **不得默认使用 9**。以下尖括号是待替换参数，不是已确认事实：

   ```powershell
   python tools/candidate-evidence/derive_fields.py C:\evidence\candidate.json --popup-hypothesis FINDER_STATE_NOTIFICATION --roulette-id <用户提供的候选值> --output-dir C:\evidence\analysis-2
   ```

3. 复核 `field-candidates.md` 与 `candidate-messages.json`。仅 `CORRECT` 且实际带负载的
   指定弹窗样本支持 roulette 字段；至少两个独立观测 id 才给出偏移候选。
   工具分别处理档案、hypothesis、opcode、方向与长度；递增比较只在同会话、同连接内进行。
   u8/u16/u32 小端解释若有多个偏移、宽度或分组匹配，工具保留全部歧义，不自动选择。
   “random”仅表示未归为常量或递增，不证明随机性。
4. **后续有证据的独立变更**中，由维护者选取已复核的 `messages` 片段填写字段，状态仍保持
   CANDIDATE。JSON 外层是研究草稿容器，不能直接作为完整档案加载；其中 `messages` /
   `message_candidates` 元素符合真实 message/field schema。工具不覆盖已发布档案，
   不填写 `mentor_roulette_id`。部分支持需显式 `--field` 选择，详见
   [工具说明](../tools/candidate-evidence/README.md)。
5. 在**第二次独立会话**中复现字段，覆盖不同随机任务与指导者任务，交叉核对弹窗、进出、
   取消等语义，并增加离线回归 fixture。确认偏移、长度、方向、id 的证据与独立复审齐全后，
   才能在后续另行审批的变更中讨论 **VERIFIED** 提升；同时遵守本指南 §1–5 的正式链路验收。
   本批不执行这一步，也不提升 opcode 档案、填写 mentor id 或修改当前的 live 状态。

本批交付证据限于 SQLite、合成报文、真实本地命名管道、离线工具及 Qt 离屏截图。
没有本机排本数据，不能将测试全绿或 `DRAFT_READY` 视为真机协议验证成功。

### 7.3 时间线的推断规则（2026-09-06 真机记录）

2026-09-06 的一次导随（国服 `2026.08.05`，逆转要害沙斯塔夏溶洞）给出了下列事实，
时间线的推断规则以此为依据：

| 事实 | 依据 |
|---|---|
| 每个 `ZONE_LOAD` 簇对应一次区域切换，**同一连接上的第一个簇即登录本身** | 会话 01:49 开始，第一个簇 01:49:18 |
| 进入副本、离开副本**都不新建连接**（连接标签 `e8315cb5eb47` 全程不变） | 三个簇同一连接：01:49:18 / 01:52:27 / 02:01:47 |
| 簇时间与 ACT 一致 | ACT 记录该副本区域于 1:52:27 开始，最后一场战斗（克拉肯）约 02:01:35 结束；簇 02:01:47 即离开 |
| 仅按簇顺序两两配对不成立 | 旧规则把“登录 → 进本”配成了一场，把真正的离开留为“未配对” |

同一会话还更正了两个候选名称（用户确认 01:52:02 点击的是“确认进入”，没有取消）：

| 报文 | 旧理解 | 现在的理解 |
|---|---|---|
| C2S `0x034b`（24 字节） | 取消排本 | **`FINDER_ACTION`**：对副本查找器的操作，取消与确认进入发送的是同一个包，动作类型应在负载中 |
| S2C `0x0323` ×2（40 字节） | 弹窗 | **状态更新**：紧跟在操作之后 1 秒内的回执，取消与确认之后都会出现 |
| 弹窗本身 | — | 应在登记与 `FINDER_ACTION` 之间到达，**尚未命名** |

为避免依赖推测，观测器新增**排本窗口采样**（`QUEUE_WINDOW_SAMPLE`，迁移 0006）：自
`QUEUE_REGISTRATION` 起，至该连接的下一个进本簇、2 小时上限或会话结束为止，
将该时间段内每一种 (方向, opcode, 长度) 合并为一行，记录首次时间、首个报文的摘要与出现次数
`occurrences`。该采样只记录元数据，不保存负载，每个窗口最多 512 种。弹窗报文即窗口内、
登记之后、`FINDER_ACTION` 之前 `occurrences = 1` 的那条 S2C 报文。

由此得到桌面端的规则：连接上的第一个簇为登录；**状态更新（`FINDER_STATE_NOTIFICATION`，
2 秒内合并为一条）之后 3 分钟内的第一个簇为进入副本（推断）**，再下一个簇为离开副本（推断），
两者配为一场；其间没有状态更新的簇一律显示为“换区”，不配对，也不作推测。
已知盲点：取消之后 3 分钟内传送会被误判为进入副本，用户核对时选择“错”。
上述结论均为推断，因此每一行都需要用户核对；字段级判定有待 §7.2 的离线推导。

这也回答了中途启动能否自愈的问题：进入副本不更换连接，因此登录之后才开始的监听不会在
进入副本时恢复，只能登出到标题画面并重新登录。

的两次弹窗相隔 97 秒后才进入副本。
运行规则见 [state-machine.md](state-machine.md) §3.2、§3.3 第 4 条、§3.5、§3.10：

1. 弹窗且编号为 9 → 创建记录（`MENTOR_MATCHED`）。申请后的回执（第 9 字节 5 / 7）与离开后的
   状态更新（第 9 字节 1）被字段约束拒绝，不会误开记录。
2. 120 秒内第一次换区 → `ENTERED_DUTY`；120 秒之后才换区 → `CANCELLED_BEFORE_ENTRY`。
3. 进入副本后的下一次换区 → 离开。档案没有 `DUTY_RESULT`，因此结果为 **`UNKNOWN`、待复核**：
   记录出现在仪表盘的“待复核”中，打开后用“修正”填写通关或离开。本软件**不会**按时长推测通关。
4. 中途启动的问题仍只能通过在登录前开始抓包解决。这两条消息都在服务器方向，该方向偶尔能
   自行对齐，但不能作为依赖。

候选验证可以持续开启：它不再阻挡正式记录，副本内采样会将进入副本至离开副本之间每种报文的
首次时间、末次时间与出现次数记入账本。通关报文应为**离开前最后出现、整场只出现一次**的
S2C 报文。找到该报文并在档案中补充 `DUTY_RESULT` 之后，待复核这一步即不再需要。

### 7.6 补丁日：本机校准（0.3.0 起的主路径）

补丁之后随包档案不再匹配。此时不需要维护者介入，也不需要新版本软件：

1. 先启动本软件，再登录游戏。捕获页显示“游戏更新到了新版本，正在重新校准”，抓包以计数模式运行。
2. 正常完成一次随机任务（不必是指导者任务）：申请、匹配、进入副本、完成后离开副本。
   卡片上的四项进度会依次勾选。
3. 离开副本后，横幅变为“校准完成，核对 4 件事就能开始自动记录”。点击“核对并启用”，逐条确认
   “排本：xx”、“匹配弹窗：xx”、“进入副本：xx”、“离开副本”是否属实。全部选择“对”时，本机写出档案并
   **立即**开始自动记录，侧栏“协议”显示“本机校准”。任一项选择“错”时本次校准作废，需要重新完成一次随机任务。
4. 仅当校准卡片提示“报文结构和上一版不同”时，才需要按 §7.1 进行候选验证并导出证据交给维护者。

判据与产物见 [protocol-profile-format.md §11](protocol-profile-format.md#11-本机校准档案与-calibration-模板段)。
§7.1 与 §7.2 属于维护者路径，仅在报文结构变化、或需要将本机档案提升为随包档案时使用。

## 8. 风险提醒

- 本软件不修改游戏、不注入、不自动化，但**不能代替用户承诺其账号安全**。
  是否使用由用户自行判断并承担相应风险。
- 抓包会读取本机网卡上的流量。用户应确认所处网络环境允许该行为。

  见 [privacy-boundary.md](privacy-boundary.md) §4 与已定稿的决策项 `DEC-OODLE-01`。

## 附：抓包运行但没有任何记录时应优先查看的三个字段

按下列顺序查看 `GetCaptureStatus` 的三个字段，不要先看 `parse_fail_count`：

1. `raw_packets_observed`：网卡层读取到的报文数。
   运行超过一分钟仍为 0，说明游戏流量不在这张网卡上，常见原因是加速器、VPN 或选错
   网卡，此时 `silent_reason` 为 `NO_PACKETS_ON_ADAPTER`。
2. `preexisting_connections`：开始抓包时游戏已有的连接数。
   该值大于 0 且始终解不出 IPC，即为中途接入：Oodle 的 TCP 解压状态按连接维护，这条连接
   无法解开。此时 `silent_reason` 为 `MIDSTREAM`，处理方式是退回标题画面重新登录，或先启动
   本软件再启动游戏。
3. `ingress.dropped_no_syn` / `ingress.unconfirmed_tuples`：报文已到达、但在重组阶段被丢弃的
   数量。前者偏大说明没有观察到握手，同样属于中途接入；后者偏大说明系统没有将这些连接确认为
   游戏的连接，原因可能是存在代理进程，或权限不足无法读取连接表，此时 `silent_reason` 为
   `NO_STREAM_OWNERSHIP`。

`packets_observed` 只统计**已通过重组与分帧**的报文，因此在上述三种情况下它与
`decode_errors` 会同时停在 0，界面表现正常。实际应查看的是上述三个字段
（docs/capture-diagnostics.md §5.5）。
