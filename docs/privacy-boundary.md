# 隐私与硬边界 / Privacy and Hard Boundary

> 本文件定义本项目**绝不做**的事。其中的条目是硬约束，而非建议。
> `scripts/verify.ps1` 调用 `tools/static-boundary-check/check.py` 强制检查这些约束，
> 检查失败即视为构建失败。任何放宽都必须先修改本文件并留下明确理由。

## 1. 定位

**本软件被动观察本机的网络流量，并将观察结果写入本机的一个 SQLite 文件。**

出站网络请求只有三类例外，均由采集服务发起：

- **共享校准获取**：游戏更新后本机没有可用档案时（以及 §8.2 所列在用档案仍读取索引的两种情形），
  从一个固定的公开仓库只读下载其他玩家分享的校准（§8.2）。
- **在线语音合成**（**默认关闭**）：用户开启后，播报时将本次要播报的文字发送给用户选定的语音服务，并取回读音（§8.3）。
- **更新检查与按请求下载**：每 24 小时最多一次，只读取本项目发布页上的版本号文件，与本软件自身的版本比较；
  发现新版本时仅在界面上提示一句（§8.4）。只有用户点击「下载并安装」后，采集服务才从本项目发布页下载该版本的
  安装程序及其公布的 SHA-256，两者一致才保留文件；只有用户再点击「立即安装」后，桌面端才启动该安装程序并随即退出（§8.6）。
  不自动下载，不自动安装。

除该条播报文字外，本软件不向任何地方上传数据。

安装程序另有一次下载：仅在安装过程中、且本机没有 Npcap 时，从 Npcap 官方站点下载其官方安装程序（§8.5）。
安装完成后运行的软件不再涉及这一下载。

### 2.1 静态检查的放行范围

规则的匹配范围、各自的放行与登记的标记以 `tools/static-boundary-check/rules.json` 为准，本节说明其中涉及上表的放行。
规则匹配的是写法，不是意图：一条命中只说明某一行用了被禁止的名字，放行则必须按仓库相对路径精确指定，或在该行登记标记。

- **`INJ-009` 只放行驱动本软件自身进程的代码。** 采集服务的父进程看门狗
  （`src/Collector/Diagnostics/ParentProcessWatchdog.cs`）用 `Process.GetProcessById`、`StartTime` 与 `WaitForExitAsync`
  打开**桌面端进程**，等待其退出并核对其启动时间，使桌面端被强行结束后采集服务随之停止。此外只放行启动、等待与结束
  采集服务或替身父进程的集成测试与单元测试，以及运行子进程（`dotnet`、采集服务、静态分析工具）的脚本
  `scripts/package.ps1`、`scripts/static-analysis.ps1`、`scripts/verify.ps1` 与一个打包测试。随软件发布的抓包代码
  一律不放行。以行内标记逐行放行的 `INJ-009` 命中都与进程句柄无关：SQLite 连接自身的句柄（`SqliteConnection.Handle`，
  位于 `src/Collector/Storage/SqliteDatabase.cs` 与单元测试 `tests/Collector.UnitTests/DatabaseIntegrityCheckTests.cs`）、
  注释中为说明取值格式而点名的 `Process.StartTime`（`src/Collector/CommandLineOptions.cs`），以及测试夹具结果记录的
  `ExitCode`（`tests/Collector.IntegrationTests/RecoveryEndToEndTests.cs`）。标记的规则见下文。
- **本软件对自身进程的其他操作。** 下列操作针对的是本软件自己的进程或内核对象，不涉及游戏进程，也不在上表禁止之列：
  桌面端读取自身进程的创建时间（`GetProcessTimes(GetCurrentProcess())`）并作为 `--parent-start-time` 传给采集服务；
  桌面端读取自身令牌的用户 SID（`OpenProcessToken(GetCurrentProcess())`），据此算出管道名，并在连上管道后用
  `GetSecurityInfo` 读取管道的所有者，只接受当前用户（或其令牌的默认所有者）的管道；采集服务用 `WaitNamedPipe`
  询问管道是否存在；两个进程用命名事件与命名互斥体（`Local\<管道名>.stop`、桌面端的单实例互斥体与唤起事件等）
  协调停止与单实例；采集服务无应答时，桌面端用系统自带的 `tasklist` / `taskkill` 核对并结束 `serve.pid` 所记的
  采集服务进程。
- **`NET-009` 只放行安装程序中创建下载页的那一行。** 安装程序在缺少 Npcap 时以 Inno Setup 的下载页下载
  Npcap 官方安装程序（§8.5）。`installer/MentorRecorder.iss` 不再按路径整体放行，只有创建该下载页的一行带有登记在案的
  行内标记（登记的命中原文为 `CreateDownloadPage(`），该文件中其他任何下载写法照常报错。其余脚本、工作流、QML 与
  桌面端不得自行下载或请求网络资源，桌面端也不得以 `load` / `setSource` 把远程地址交给 QML 引擎。任何代码也不得把远程地址
  交给 XML 读取接口（`XDocument.Load`、`XmlReader.Create` 等）。
- **`NET-010` 只放行开发期的数据表生成器。** Python 代码不得引入或调用联网模块；按路径放行的只有
  `tools/duty-data-generator/generate.py`，它在开发期从公开来源下载副本数据表，是仓库中唯一联网的 Python 文件。
  `tools/shared-calibration/` 的 Python 只读取保存下来的 `gh` 输出，不需要放行。
- **行内标记。** 一行可以用 `BOUNDARY-ALLOW(<规则编号>): <理由>` 解除**该行**上**该条**规则的**一处**命中，
  其他规则照常检查。每个标记都按「文件 + 规则编号 + 命中原文」逐个登记在 `rules.json` 的 `allow_markers` 中，
  只有该行上该规则恰好只有一处命中、且其原文与登记一致时才生效；同一行出现该规则的第二处命中，或命中换成了
  其他写法，都会被报出并使检查失败。未登记的标记、没有解除任何命中的标记、登记了却找不到的标记，以及写了未声明
  规则编号的标记，同样使检查失败。每个生效的标记连同它解除的命中原文列在检查输出中。标记只用于三种情形：
  说明边界的代码在注释中点名一个被禁止的成员（例如解释为何不用它）；某行的唯一命中并非被禁止的对象（同名而无关的
  成员）；以及上一条所述安装程序中创建 Npcap 下载页的那一行。
- **检查不完整即失败。** 文件无法读取或超出大小上限、目录无法列出、扫描根缺失、扫描到零个文件，都使检查以失败告终，
  而不是报告通过。

## 3. 注入式抓包（禁止）

Machina.FFXIV 较新的版本支持 **Deucalion**，即一个被注入到游戏进程中的 DLL 钩子。
该方式能够获得解密后的数据，代价是**向游戏进程注入代码**。

**本项目永不启用它。**

具体约束：

1. 本项目不使用 Machina 的 `FFXIVNetworkMonitor`，因此不存在可以开启 Deucalion 的监视器。
   报文由 `src/Collector/Capture/NpcapPacketReader.cs` 读取：经 SharpPcap 打开所选网卡对应的唯一一个 Npcap 设备
   （不开启混杂模式），设置过滤器 `ip and tcp and host <所选网卡的本机地址>`，以非阻塞方式逐包读取。
   Machina.FFXIV 只承担三项工作：读取系统 TCP 表以确认连接归属、获取 Oodle 解压函数、在已确认归属的连接上
   做 TCP 重组与报文包解码（`MachinaCaptureSource.cs`、`FirstPacketMonitor.cs`）。静态规则 `DEU-001` 禁止把 `UseDeucalion` 设为开启，
   `DEU-002` 与 `DEU-004` 禁止调用 Deucalion 的接口及其注入载荷的加载入口。
2. 只经由 Npcap 抓包，不存在 raw socket 实现，也不提供 raw socket 回退。Npcap 不可用时直接返回
   `ERR_NPCAP_MISSING`。静态规则 `CAP-003` 禁止出现 `NetworkMonitorType.RawSocket`，`CAP-004` 禁止 raw socket
   抓包实现，`CAP-006` 禁止绕过 SharpPcap 直接加载 pcap 原生库。诊断中的 `monitor_type` 恒为 `WinPCap`，
   表示经 Npcap 的 WinPcap 兼容接口抓包。
3. Machina.FFXIV 的 NuGet 包在 `lib/netstandard2.0/` 中附带了原生注入载荷
   `deucalion-<version>.dll`。仓库根目录的 `Directory.Build.targets` 定义了
   `StripInjectionPayloadFromOutput` 目标，将其从**所有**构建输出中移除，
   避免发布目录中出现注入 DLL。静态规则 `DEU-003` 禁止再次引用它。
4. `CaptureStatus.injected_hook_enabled` 在 IPC 契约中固定为常量 `false`，
   并显示在界面的诊断页，供用户自行验证这条边界。

## 4. Oodle 与"加载游戏本体"的边界

FFXIV 的流量使用 Oodle 压缩。Machina.FFXIV 通过 `OodleImplementation` 选择获取
Oodle 解压函数的方式，可选项包括：

| 取值 | 做法 |
|---|---|
| `LibraryTcp` / `LibraryUdp` | 加载独立的 `oo2net_9_win64.dll` |
| `FfxivTcp`（Machina 的默认值） | **将游戏可执行文件从磁盘复制到临时目录，再用 `LoadLibraryW` 把该副本加载进本软件自身的进程**，随后在这份镜像中做特征扫描（sigscan）定位 Oodle 函数 |
| `KoreanFfxivUdp` | 同上，使用韩服的特征 |

**边界含义（必须向用户说明）：**

- 该过程**不是**进程注入。本软件不打开游戏进程，不写入其内存，不创建远程线程。
  被加载的是**磁盘上游戏二进制的一份副本**，加载目标是**本软件自身的进程**。
- 但它**确实**意味着本软件会**读取并加载游戏的可执行文件**。该事实必须
  在界面与 README 中明示，不得隐藏于实现细节之中。
- 从版权角度看，本项目既不复制也不分发游戏二进制的任何部分。副本是运行时在本机产生的
  临时文件，由本软件负责清理：正常退出时删除，未能删除的登记在清单中，于下次启动时删除（§4.2）。

### 4.1 决策项 `DEC-OODLE-01`：已定稿（DECIDED）

> **结论**：默认 **选项 B（`FfxivTcp`）**；当用户自备 `oo2net_9_win64.dll` 时
> 自动改用 **选项 A（`LibraryTcp`）**。选项 C 不采用。

曾评估的三个选项：

- **选项 A**：`LibraryTcp` 配合用户自备的 `oo2net_9_win64.dll`。
  优点：完全不接触游戏二进制。缺点：该 DLL 属于 RAD Game Tools 的专有组件，
  **本项目不分发它**，需由用户自行提供，可用性差。
- **选项 B**：`FfxivTcp`，即将游戏可执行文件复制到临时目录，把**副本**加载到**本软件自身的进程**做 sigscan。
  优点：开箱即用。缺点：必须向用户明示本软件会读取游戏可执行文件；
  临时副本必须保证删除。
- **选项 C**：不解压 Oodle 内容，只依赖未压缩或可判别的信号。
  优点：边界最清晰。缺点：无法获得判定所需的字段，功能大幅受限。

**取舍理由**：

1. 选项 C 将使本软件无法完成其唯一的功能目标。FFXIV 的 IPC 流量经 Oodle 压缩，
   不解压即无法获得 `content_id` / `roulette_id` 这类判定必需的字段。
   最清晰的边界对应的是零功能，该取舍不可接受。
2. 选项 A 的边界更清晰，因此**在用户提供该 DLL 时优先采用**。
   路径记录在 `application_settings` 的 `capture.oodle_library_path`，
   该项非空时切换到 `LibraryTcp`。本项目**不分发**该 DLL，也不提示其下载来源。
3. 选项 B 作为默认值，因为绝大多数用户不会自备 RAD 的专有 DLL。

**实际行为对照**：

| | |
|---|---|
| 读取游戏**可执行文件**（磁盘上的字节） | **是** |
| 把该文件的**一份副本**复制到临时目录 | **是** |
| 用 `LoadLibraryW` 把**副本**加载进**本软件自身的进程** | **是** |
| 打开游戏进程的句柄 | 否 |
| 读写游戏进程的内存 | 否 |
| 在游戏进程中创建远程线程 / 注入 | 否 |
| 复制或分发游戏二进制的任何部分 | 否（副本为本机运行时产物，使用后由本软件删除，见 §4.2） |

**必须遵守的三条约束**（实现均已落实）：

- **(a) 明示**：`GetStatus` 返回 `oodle_mode` 与 `reads_game_executable`。
  桌面端在设置页"关于"常驻显示该信息（「读取游戏可执行文件」一项），该页「查看软件说明」打开的说明窗口
  「这个软件做什么、不做什么」同样写明，捕获诊断页的维护者工具中也列出这两个值，脱敏诊断报告中同样包含。
  README 与 [third-party-licenses.md](third-party-licenses.md) §2.3 亦写明这一点。
- **(b) 不分发**：既不分发 `oo2net_9_win64.dll`，也不分发游戏的任何文件。
- **(c) 使用后删除**：见 §4.2。删除过程**有清单、可核对**，而非仅为一项承诺。

### 4.2 临时副本的清理

Machina 在释放库时会尝试删除自己产生的临时副本，其诊断信息中即包含
"FreeLibrary could not delete temp file" 一条。该尝试**可能失败**：
加载器仍持有映像时删除操作会失败，用户的临时目录中因而残留一整份游戏二进制。

因此 `src/Collector/Capture/OodleTempCopyCleaner.cs` 只登记本次抓包创建的 native
实例实际持有的临时副本路径，且路径必须位于 Machina 专属临时子目录。它不扫描 TEMP，
不按文件名删除该目录中的文件，也不凭文件大小、时间或内容相似来猜测所有权：未经登记的副本
不属于本软件，同一目录中可能有其他基于 Machina 的程序刚复制、尚未加载的副本。初始化失败时也尝试
从该实例登记路径；依赖内部结构不兼容或无法确认所有权时保留文件。

释放本次实例后，仅重试删除已登记路径，并记录删除数量。删除失败的路径继续保留，
供后续清理重试；不会扩大删除范围或处理其他实例的文件。

登记依赖 Machina 在复制之前先记下副本路径、并在初始化线程上写出诊断信息的行为，本软件在这些时刻读取路径。
进程恰好在副本复制完成之后、本软件读到其路径之前被结束时，该副本未及登记，本软件不会删除它；
它位于 `%TEMP%\Machina.FFXIV\` 下，可由用户手动删除。

**跨进程的清单。** 登记过的路径同时写入数据库目录下的清单文件
`<数据库目录>\oodle-temp.json`（`--db` 未指定时为 `%LOCALAPPDATA%\MentorRecorder\`）。
正常监听、界面上的「开始验证」与命令行取证 `--capture-trace` 使用同一份清单。每次开始监听都有各自的登记，
登记时把自己的路径并入清单，删除后只从清单中移去已删除的路径，不改写其他条目；清单为空时删除该文件。
下次 `CollectorHost.Open` 时，
清单中**仍然存在**且**确实位于 Machina 专属临时子目录直下**的条目会被删除，并记录一条
`startup/oodle_temp_copy_reclaimed {count}`。该通路存在的原因是进程可能没有机会
执行 finally 块，例如被任务管理器结束、断电，或被不执行优雅停止的调用方终止。
清单代表**确定的所有权**，因此不违反"不扫描 TEMP"这一条。

**可核对。** `--capture-doctor`（以及 `--json` 的 `oodle_temp_copies`）报告清单中
剩余的副本数量、占用字节数与已不存在的条目数。该命令读取清单，不枚举临时目录。
格式见 [capture-diagnostics.md](capture-diagnostics.md) §9.3。

**退出路径。** 进程退出时 `CollectorHost.Dispose` 先停止抓包再关闭数据库，正常退出
路径上该步骤总会执行。桌面端关闭时不直接结束 Collector：它先置位 Collector 的停止事件
`Local\<管道名>.stop` 并最多等待 10 秒，使采集服务走与 Ctrl+C 完全相同的停止路径，
超时后才兜底结束进程。因此关闭桌面端这一最常见的退出路径同样会清理副本、关闭会话行并写入停止日志。

## 5. 原始报文的处理

- 抓包过滤器只按本机地址过滤（`ip and tcp and host <所选网卡的本机地址>`），不按远端地址过滤，
  以免在新连接建立与过滤条件更新之间漏掉 Oodle TCP 初始化数据（诊断日志记为 `remote_ip_filter = false`）。
  Npcap 因而会把同一本地网卡上其他程序的 TCP 报文短暂送入进程内的有界缓冲区；只有系统 TCP 表确认属于
  游戏进程的连接才会被解码，其余报文在缓冲区中丢弃。无关包不进入业务解析、trace、日志或数据库，也不会落盘。
- 抓包回调复制出**判定所需的最小字段**后立即释放缓冲区。
- 有界队列中的元素在解析后立即归还，不做任何持久化。
- `run_events.detail_json` 只允许：opcode 编号、方向、报文长度、时间戳、
  以及被解析出的 id 型字段（`content_id` / `territory_id` / `roulette_id` / `job_id`）
  与档案 id。
- **禁止**写入：原始字节、十六进制转储、聊天内容、角色名、队友信息、
  IP 地址、MAC 地址、任何其他玩家的可识别信息。
- 诊断日志同样受此约束，且不依赖调用方自觉。`RotatingFileLogger.Sanitize`
  在落盘前把任意用户的 profile 路径、Windows SID、IPv4 与 IPv6 字面量、
  以及连续 16 位及以上的十六进制串分别替换为 `%USERPROFILE%` / `[sid]` /
  `[ip]` / `[ip6]` / `[hex]`。阈值取 16 是为了保留用作 id 的短哈希前缀。
  适配器指纹为 12 位，UUID 分段更短；这些前缀不泄漏信息，却是区分两张网卡、
  两个会话的唯一依据。该行为由 `DiagnosticsLogHygieneTests` 强制，无跳过用例。
- 日志按大小滚动：单文件上限 **2 MiB**，最多保留 **5** 个文件，另按 **7 天**清理
  （[capture-diagnostics.md](capture-diagnostics.md) §8）。
- 用户显式开启验证时，会额外生成 opcode 级取证文件。取证文件有**两条**通路，产物格式相同：
  命令行 `--capture-trace <out.jsonl>` 写入用户指定的路径；界面上的"开始验证"写入
  `<数据库目录>\traces\<时间戳>-<GUID>\`。两条通路均不含负载字节、地址或解析字段。
  每条消息只有序号、时间（相对毫秒、本机 UTC 时间与报文所属压缩包的服务器 epoch）、连接标识、
  方向、段类型、opcode、负载长度和负载 SHA-256 的 12 位前缀。连接标识是已哈希连接键的前 8 位，
  只用于在同一份取证内区分连接，不含地址，跨会话不可关联；summary 另按该标识汇总每条连接的消息数。
  标记只接受 `queued` / `pop` / `entered` / `victory` / `left` 五个固定词。
- 取证文件的边界由**具体数值**限定：
  - 行数：消息行默认上限 20 万（`--max-lines`，最多可设为 25 万，即 `--trace-report` 能读取的行数），
    标记行上限 1 万；达到上限后只计数、不再写入，并在 summary 中标记 `truncated`。
  - 时长：界面通路每次会话最长 **2 小时**（从开始验证起计，含等待游戏或重启的时间），到时自动停止；
    命令行 `--duration-seconds <n>` 最大
    86400，**省略该参数或取 0 表示不限时长**，只由行数上限、游戏退出或 Ctrl+C 封顶。
  - 保留：界面通路的会话目录只保留**最近 10 个**，且不超过 **7 天**；启动时与每次会话
    结束后各清理一次，只删除本服务自身按 `<时间戳>-<GUID>` 命名写下的整个会话目录。
    命令行通路写入用户指定的文件，本软件不清理该文件，也不覆盖已有输出。
- 摘要前缀只用于本地关联，不构成加密或匿名化保证；整份 trace 不作为公开 issue 附件。
  完整格式见 [capture-diagnostics.md](capture-diagnostics.md) §9.2。
- 除下述经任务书明确批准的研究模式外，发布构建不保存原始负载；既有 trace、
  正式记录和诊断导出继续执行上述限制。

### 5.1 研究模式：被动候选验证的显式例外

目的仅为维护者离线核对候选报文的字段偏移，事实源为
passive-validation-batch.md（内部工作文档，不随仓库分发） §1、§2、§4.3 和 §5。
候选档案保持 CANDIDATE，`mentor_roulette_id` 保持空，观测不产生正式记录、统计、成就或语音。

- `capture.candidate_validation_enabled` 默认 false，`capture.research_payload_opcodes`
  默认空数组。只有前者显式开启、后者非空，且消息命中白名单时才能保存负载。
  单独开启候选验证只保存长度和摘要；清空白名单或关闭验证立即停止后续负载保存。
- 白名单仅接受候选档案中已声明、长度上界不超过 512 字节、未混淆的 opcode。
  未知或无长度上界条目拒绝加入，实际负载超过 512 字节时整段不保存，不截取前缀。
  此上限由用户于 2026-09-08 确认，并通过追加迁移同步数据库约束；默认关闭与明确白名单仍是前提。参考
  obfuscation-research.md（内部工作文档，不随仓库分发） §2.1 的混淆类型
  以及档案显式混淆集合，不推测或引入新的混淆 opcode 数字表。
- 原始字节只写入独立 `candidate_observations.payload_hex` 可空列。研究关闭时新观测的
  该列恒 NULL；ZONE_LOAD 推断锚点不带负载。禁止复制到 `run_events`、日志、trace、
  诊断报告或实时事件，普通分页查询也不返回原始负载。
- 排本窗口采样（`QUEUE_WINDOW_SAMPLE`）在排队登记到下一次进本之间记录**每一种**报文的
  方向、opcode、长度、首次时间、首个报文摘要和出现次数，用于定位尚未命名的弹窗报文。
  该采样不经过白名单，也不保存负载（`payload_hex` 恒 NULL）；每个窗口最多 512 种、15 分钟。
- 负载随观测账本保留，最多 20000 条观测 / 30 天，超出按最旧观测删除并清理关联核对历史。
  关闭研究不改写既有证据；查询、写入和导出执行保留期清理。
- 专用“导出证据”保留 `payload_hex`，因为该字段正是离线推导的输入。文件头
  `contains_raw_payload` 必须反映文件内实际存在的负载；存在时为 true，
  `research_payload_opcodes` 列出该快照内实际保存过负载的 opcode（即使当前开关已关闭）。
  不含负载时为 false 且数组为空。每行仍保留长度、摘要、会话内连接短标识和核对历史，
  不附加地址、角色或队友标识。文件及 SHA256 边车仅由现有 ExportPaths 约束写往本地允许目录。
- 负载不是匿名化数据，关闭开关不会使既有文件成为脱敏文件；专用证据及含该表的数据库备份
  可能仍含原始内容。用户在本地核对后自行交给维护者；程序不自动上传、访问网络或公开发布。

### 5.2 本机校准：不保留正文的观察

游戏更新后没有匹配档案时，本软件进入本机校准。该阶段
**只观察、不记录**。观测器持有上一版档案的报文结构，在每条报文到达时按该结构取出
轮盘编号、区域编号、职业编号等 id 类字段的值，只记录这些值以及报文的方向、opcode、长度
和时间。原始正文不保留任何字节，也不写入数据库。

0.3.4 起另在内存中保留**模板声明为选择器的字段取值**（当前国服模板为副本查找器状态编号）。
只有满足模板方向、长度、轮盘编号和普通值字段约束的报文才保留为候选；普通值字段不参与重新学习。
候选进入推断前，还必须对应同一 opcode 的已配对请求，并有按时序跟随的已知副本进入证据。
这些值均为模板指定的整数，不采集文本、坐标或角色信息。诊断的状态值计数仅覆盖已配对的
opcode，按 opcode 与字段名分组，**不与轮盘编号、连接标签或事件时间线一起导出**。

诊断计数表有固定上限，截断仅影响报告。用于判定的候选表同样有上限，但只要丢失的证据可能影响
时序或唯一性，就阻止生成可启用草稿。只有已知回执状态的冗余样本可以安全压缩。

校准产物是一份普通的协议档案（§9 的
`protocol-profiles\`），用户核对时间线后才写出。校准期间的抓包与 §6 的 fail-closed 一致：
不启用正式解析与状态机，不写正式记录；观测器仅提取上述模板字段用于校准。

| 情形 | 行为 |
|---|---|
| 未安装 Npcap | `ERR_NPCAP_MISSING` + 安装指引；运行中的软件不下载、不内置（安装程序的下载见 §8.5） |

| 事件序列出现空洞（解析队列溢出；或一条游戏连接的某一方向被放弃，且该方向本次会话交出过当前档案能解析的报文，尚无任何方向交出过时任一方向均算，见 [state-machine.md](state-machine.md) §7.5） | 进行中的记录按丢失观测收尾：已进本的判为 `INTERRUPTED`，尚未进本的记为「进本前取消」并标记待复核；**不补全** |

### 8.1 本机备份：复制整个数据库，仅写入本机

桌面端的"每日自动备份"**默认开启**，可在设置中关闭。它每天执行一次：启动后连上 Collector 时，
或程序持续运行跨过零点后的检查中（每小时检查一次日期）；导随进行中则顺延到这一场结束 5 分钟之后，其间再次匹配则继续顺延。备份写入
`<数据库目录>\backups\`（默认 `%LOCALAPPDATA%\MentorRecorder\backups\`），
保留最近 **14** 份，超出部分按时间删除；同时清理该目录中遗留超过 1 小时的
`.mentor-export-*.tmp` 暂存文件。清理范围**仅限该由本软件管理的目录**。用户在
`BackupDatabase` 中自行指定的目标目录不受影响。

备份是数据库的完整副本，因此**可能包含**研究模式保存过的原始负载（§5.1）。
备份文件不是脱敏产物，不应作为可对外分享的诊断材料。

### 8.2 共享校准获取：只读下载（2026-09-15 起的放宽）

**放宽理由。** 游戏每次更新都可能重排 opcode。本机校准（§5.2）能够重新学习这些 opcode，
但每个玩家在每个补丁后都需重复一次，至少完成一次随机任务，并排过两个不同的随机任务。
同一区服、同一客户端版本的 opcode 编译在客户端内，对所有玩家一致，因此一名玩家的校准结果可供其他玩家复用。
用户于 2026-09-15 选定"从 GitHub 自动获取、默认开启"的方案，未采用纯离线校准码（不会自动生效）、
自建服务器（需要运维，国内可达性差，需要防刷）与默认关闭（多数玩家不会发现该开关）三种备选。
设计与评审见 plans/shared-calibration.md（内部工作文档，不随仓库分发）。本条有意放宽了本文件原先
"发布出来的软件在运行时不发起任何网络请求"的承诺，放宽范围逐条列于下文。

**只读取一个仓库。** 只读 `GET` 固定公开仓库 [`Harendotes-Tang/MentorRecorder-Calibrations`](https://github.com/Harendotes-Tang/MentorRecorder-Calibrations)
（2026-09-16 建立）中的 `index.json` 与校准码文件（`.mrc`），按顺序尝试三个源：`raw.githubusercontent.com`、
`cdn.jsdelivr.net`、`fastly.jsdelivr.net`，前一个失败后才尝试下一个。除本类请求、§8.3 的在线语音合成
与 §8.4、§8.6 的更新检查及按请求下载外，其余出站行为仍然禁止：遥测、使用统计、崩溃上报、账号。
0.7.11 发布时该仓库尚未建立，该版本的请求只会得到"未找到"。

**仓库内容。** 仓库中包含玩家提交的校准码、索引 `index.json`，以及提交台账 `submissions.json`。
台账按区服与客户端版本记录每次提交的 GitHub 账号数字编号、校准码校验值、提交时间与 Issue 编号，以及该账号此前被替换掉的校准码的校验值，
仅用于执行按账号的规则：每个账号每个版本同时只保留一份有效校准码；每个账号对同一版本的提交次数、每天可提交的版本数均有上限；
某个账号提交的校准码被维护者撤回后，该账号在该区服与版本下的提交暂停，经维护者复核后才恢复。**本软件从不下载该文件**，
`index.json` 中也不含任何账号信息。发布由玩家在浏览器中提交 Issue、由该仓库的 GitHub Action 校验后完成，
Action 只使用 GitHub 默认的 `GITHUB_TOKEN`。仓库中的脚本与模板按 GPL-3.0-or-later 授权，
玩家提交的数据按 CC0-1.0 公开，提交表单中写明"提交即同意"。

**触发条件。** 下列条件同时满足时才会自动获取：区服与客户端版本已知；本机校准处于可启用状态；
采集设置 `shared_calibration_enabled` 为开启（默认开启）；并且当前版本**没有可用档案**，
或者在用的档案属于下面两种情形之一（1.4.0 起，见"已有档案时仍读取索引的两种情形"）。
游戏不必正在运行：客户端版本既可来自正在运行的客户端，也可来自本机记住的游戏安装目录（§9 的
`game-install.json`），因此软件启动后、玩家登录游戏之前即可获取。
同一区服、同一客户端版本、同一模板在 6 小时内最多自动获取一次。

**已有档案时仍读取索引的两种情形（1.4.0 起）。** 1.4.0 之前的规则是"已存在可用档案时不发出任何请求"。
实际运行中出现了两种这条规则挡住的情况：仓库撤回了一份错码，而已经在用它的机器永远读不到撤回；
仓库发布了更准的码，而在用按排本推断档案的机器永远读不到。因此放宽为：在用的档案属于下列任一情形时，
仍按上述同一节流读取一次索引——

- **在用的是其他玩家分享的校准**（来源为共享校准）：索引可能已把它撤回，或提供了更准的码；
- **在用的档案按排本推断匹配**（无论来源是本机校准、共享校准还是随包档案）：认服务器报文的码比它更准。

随包档案在用、或本机校准出来的、认服务器报文的档案在用时，仍然一次都不发出请求；
共享档案完整记录过一次并且判据全部通过、校准随之结束后，也不再读取。
这两种情形下索引中的码若要启用，就会替换本机已可用的档案，因此须排本与进本报文也核实通过（见下文"客户端行为限制"）。

读取的**请求与没有档案时逐字节相同**：同一个 `GET`，没有查询串、没有正文、没有任何标识信息，
与本节下文"请求不携带标识信息"完全一致。这次读取**不上传任何内容**，索引里没有、请求里也没有任何本机信息，
对端只能看到与平时相同的一次下载。读取的时间与结果记录在脱敏诊断报告的 `calibration.shared.recheck` 中。

**界面呈现与关闭方式。**

- 设置页"通用"中的开关「游戏更新后获取其他玩家的共享校准」对应上述 `shared_calibration_enabled`。其描述写明这是默认开启的一类联网请求（另两类是 §8.3 的在线语音，默认关闭，与 §8.4 的更新检查，默认开启），且不携带任何可识别玩家的信息。
  关闭后将取消进行中的获取并丢弃已下载的候选；已核实生效的共享档案不受影响。设置页"关于"中「查看软件说明」打开的说明窗口同样写明该项联网行为与关闭方式。
- 捕获诊断页的校准卡片说明共享校准所处的阶段：正在获取、等待核实、已使用、核实不符已改为本机校准、未取到、无人分享该版本、已按玩家选择改为本机校准。
  卡片不显示校准码、校准码编号、十六进制或拒绝原因记号。
- 「立即检查」只在本机仍处于校准状态时出现，用于使采集服务立即获取一次。该操作同样受上述条件、开关与总开关限制，
  只是不受 6 小时节流限制；不满足上述触发条件时（例如随包档案在用）不发出任何请求。
- 「导入校准码」供玩家粘贴他人提供的校准码。导入过程不联网，也不受开关影响；导入的校准码同样须先在本机流量中核实。
  导入时只比对本机此前下载到的索引，不发出请求：索引列出的码按下载的码对待；索引已撤回的码拒绝导入；
  任何索引都不认识的码须排本与进本全部核实通过后才生成档案，在此之前不产生记录（1.1.0 起）。
- 「不用共享的，我自己校准」先弹出确认，随后撤下正在使用或正在核实的共享校准。在执行「清空进度并重新观察」之前，该版本不再获取、导入或绑定共享校准。
- 按排本推断匹配的共享校准核实通过后，卡片先说明该记录方式的代价，即记录中的匹配时间为申请排本的时间；玩家点击一次「同意，开始记录」后才会启用。

0.7.11 仅实现采集服务一侧，不含上述界面。该版本只能通过下文的**总开关**关闭下载，需要用户同意的共享校准不会启用。
0.7.12 起界面齐全，包含设置开关、立即检查、分享、导入与同意提示；存放共享校准的公开仓库亦已建立。

**请求不携带标识信息。** 请求没有查询串、没有 Cookie、没有安装 id、没有账号；除固定的
`User-Agent: MentorRecorder`（不带版本号）外不附加任何请求头。URL 中只有固定的仓库路径，
以及索引给出的提交号、区服与客户端版本号，这些均为公开信息。
与任何网络连接一样，对端服务（GitHub、jsDelivr 及其 CDN）可以看到请求的来源 IP 地址与发生时间。

**附带流量。** 以下流量由操作系统发起。本软件不额外增加这些请求，但它们确实会发生：

- DNS 解析上述三个主机名；
- 遵循系统代理设置时，Windows 可能执行代理自动发现（WPAD / PAC 脚本）；
- 校验 TLS 证书时，Windows 可能访问证书机构，获取证书链与吊销信息（CRL / OCSP）。

**客户端行为限制。**

- 不跟随重定向，任何 3xx 均按失败处理，只接受 2xx。
- 不存储 Cookie，不发送 Windows 凭据。
- 响应的最终主机必须在上述三个主机的白名单内。
- 每个源的每次请求（索引或一份校准码）连接与读取合计 10 秒超时。
- 边读取边统计字节：索引超过 64 KB、单个校准码超过 4 KB 立即断开；校准码解压后另行限制为 16 KB。
- 索引按严格格式逐条校验，格式不符的条目丢弃；校准码的哈希必须等于索引中登记的 `code_sha256`，否则丢弃。
- 下载的校准码**不是档案**。它只写入 §9 的 `shared-calibrations\`，须先在本机流量中按结构核实，
  才会生成档案并用于记录（plans/shared-calibration.md §4、§18）。候选按索引给出的提交人数从多到少排列，
  人数相同时没有冲突标记的在前，再依次按首次发布时间与校验值排列；通过核实的候选中，认得出服务器匹配报文的码
  优先于按排本推断的码。
- 核实的门槛取决于这份码与本机的情况。公开仓库列出的码，只有同时满足下列条件时，才在登录时换区报文按结构核实
  通过后即生成档案并开始记录，排本与进本报文在记录中继续核实：本机当前没有可用档案；仓库没有给它标冲突标记；
  至少有一名提交者；没有提交人数比它更多的候选。其余的码，即会替换本机已可用档案的、带冲突标记的、另有提交人数
  更多的候选的，以及未在仓库发布的导入码，须排本与进本报文也核实通过才生成档案，在此之前不产生记录。
  每份候选实际采用的门槛见脱敏诊断报告中各判据的 `gate`（[capture-diagnostics.md](capture-diagnostics.md) §9.6）。
- 无论门槛如何，两个抓包完整的会话都对不上时撤下档案，它生成的记录标记待复核。每份共享档案开始记录的时间随档案
  保存在本机（§9 的 `state.json`），撤下时只标记这份校准自己生成的记录，重启之后同样如此。采用磁盘上已有的共享档案
  之前，先核对上次读到的索引是否已撤回它；已撤回的立即撤下，它生成的记录标记待复核。

**不上传数据。** 在共享校准一侧，本软件不向任何地方发送数据。校准卡片上的「分享给其他玩家」只在本机校准完成、
且当前正在使用本机校准档案时出现。点击后由系统浏览器打开 github.com 上预填的 Issue 页面，并将校准码复制到剪贴板。
页面内容对玩家可见，是否提交由玩家在浏览器中自行决定。
校准码过长、无法放入地址时只复制，不打开浏览器；桌面端只将 `https://github.com/` 下的地址交给浏览器。

**只有采集服务联网。** 桌面端继续禁止 `QNetworkAccessManager`（`NET-006`），打开网页一律交由系统浏览器处理。

**总开关。** 环境变量 `MR_DISABLE_SHARED_FETCH=1` 使获取完全不发生：不解析主机名，不建立连接。
任何非空且不为 `0` / `false` 的值同样生效。`scripts/verify.ps1`、`scripts/test.ps1`、`scripts/package.ps1`
均设置该变量，因此验证、测试、打包期间不会联网。

**静态检查约束。** `NET-006` 仍在全仓范围内禁止 HTTP 客户端（`HttpClient` / `WebClient` / `QNetworkAccessManager`，
以及 `HttpMessageInvoker`、`SocketsHttpHandler`、`WebRequest`、WinHTTP、WinINet、`URLDownloadToFile` 等），只放行三个文件，
且按仓库相对路径精确匹配，不按文件名或目录名匹配：本节的 `src/Collector/Protocol/Sharing/SharedCalibrationClient.cs`、
§8.3 的 `src/Collector/Speech/OnlineSpeechClient.cs`，与 §8.4 的 `src/Collector/Update/UpdateCheckClient.cs`。
`NET-007` 管控主机名片段，每个片段有各自的放行名单。`jsdelivr` 只能出现在共享校准获取客户端、公开仓库脚本的镜像目录
`tools/shared-calibration/`，以及开发期下载公开数据表的 `tools/duty-data-generator/generate.py`；
`githubusercontent` 另有 `github-content-hosts` 变体，除上述三处外，还可以出现在 §8.4 的更新检查客户端中，此外任何位置都报错；
`tts.speech.microsoft.com` 只能出现在在线语音客户端（§8.3）。各处放行互不通用：共享校准客户端中出现语音主机名，
或语音客户端中出现共享校准的源，同样报错。`NET-008` 禁止直接使用套接字、域名解析、Ping 与 SmtpClient，
没有任何放行，三个客户端同样只经由 HTTP 客户端联网；`NET-009` 禁止脚本、工作流、QML 与桌面端自行下载或请求
网络资源，也禁止桌面端把远程地址交给 QML 引擎、任何代码以 XML 读取接口从远程地址加载，只以一个登记在案的行内标记
放行安装程序中创建 Npcap 下载页的那一行（§2.1、§8.5）；`NET-010` 禁止 Python 代码引入或调用联网模块，
只按路径放行开发期下载公开数据表的 `tools/duty-data-generator/generate.py`。

### 8.3 在线语音合成：仅发送播报文字（2026-09-16 起的放宽，默认关闭）

**放宽理由。** 播报原本只使用 Windows 自带的语音引擎。部分系统未安装中文语音，已安装的合成效果也较为生硬，
玩家在副本中难以听清"匹配成功""副本结算"一类提示。用户于 2026-09-16 选定"本机语音 + 在线语音"的方案，
同时支持微软 Azure 语音与 OpenAI 兼容接口（plans/ui-redesign-2026-09.md（内部工作文档，不随仓库分发） §1 决策 6、§6）。
本条有意放宽了 §8 中"只有一种出站请求"的承诺，放宽范围逐条列于下文。

**默认关闭。** 只有同时满足下列条件时才会发出请求：用户在设置「播报」中将语音引擎选为在线语音；已选择服务并填写地址；
已填写自身的密钥；当前确有一条文字需要播报，或用户点击了「测试」。服务一栏为"不使用"（`provider = none`）时不发出任何请求。
首次切换到在线语音时，桌面端先弹出确认框，说明发送内容、发送目标与关闭方式。

**发送内容仅为该条播报文字。** 请求正文是本次要播报的文字，即模板渲染后的一句话，可能含副本名与进度数字，
另附用户选定的音色与语速；请求头中携带用户自身的密钥。请求不包含账号、角色名、队友、游戏报文、记录编号、安装编号，
也不包含任何可识别本机的信息。与任何网络连接一样，语音服务可以看到请求的来源 IP 地址与发生时间，
并按其自身的隐私政策处理收到的文字。服务由用户选择，密钥由用户自行申请；本软件不代替用户做出该决定。

**发送目标由用户选择。**

- 微软 Azure 语音：`POST https://<区域>.tts.speech.microsoft.com/cognitiveservices/v1`。区域由用户填写，
  必须是 2–32 个小写字母或数字（`^[a-z0-9]{2,32}$`），因此地址只能位于微软的该域名下。
  请求头只有密钥（`Ocp-Apim-Subscription-Key`）、`Content-Type: application/ssml+xml`、
  输出格式（`X-Microsoft-OutputFormat: riff-24khz-16bit-mono-pcm`）与固定的 `User-Agent: MentorRecorder`（不带版本号）。
  正文为 SSML，文字与音色名按 XML 转义。
- OpenAI 兼容接口：`POST <用户填写的地址>/audio/speech`，`Authorization: Bearer <密钥>`，JSON 正文为
  `{model, input, voice, response_format: "wav", speed}`。地址必须是 `https://`，仅本机回环地址
  `127.0.0.1`、`::1`、`localhost` 可以使用 `http://`，供用户在本机运行的服务使用；地址不得带用户名、密码、查询串或片段。
- 桌面端设置页的说明为"播报文字会发送到 <主机>"，主机名由采集服务给出（`GetSpeechSettings.target_host`）。

**密钥只保留在本机。**

- 采集服务使用 Windows DPAPI（当前用户）加密后保存为数据目录下的 `speech-key.bin`。更换 Windows 账户或更换机器均无法解密。
- 密钥与其发送目标主机绑定。更换服务、修改区域或修改地址而未重新填写密钥时，旧密钥立即删除；为某一服务填写的密钥不会被发送给另一服务。
- 密钥只写不读。桌面端提交后，采集服务的任何应答都不携带密钥，只返回 `has_key`。密钥不写入日志、脱敏诊断报告与数据库。
- 日志只记录错误码与主机名，不记录请求正文、响应正文或请求头。
- 落盘的只有 DPAPI 密文。运行期间，密钥会以普通字符串短暂驻留在采集服务的内存中，即经命名管道接收时与每次发送请求时。
  .NET 无法可靠地清零字符串，因此能够读取该进程内存的一方（调试器、崩溃转储）有可能看到密钥。加密前的字节缓冲会立即清零。

**读音缓存在本机。** 取回的读音写入数据目录下的 `tts-cache\<sha256>.wav`，键为服务及其地址或区域、所用模型、音色、语速与文字共同计算出的哈希，不包含密钥。更换服务地址或模型后不会复用旧配置的读音。
同一文字再次播报时直接使用缓存，不再发出请求。该目录上限 20 MB，超出部分按最近使用时间淘汰。桌面端只播放 `tts-cache\` 中的文件。
「测试」不读取缓存，每次均发出一次真实请求。

**客户端行为限制。**

- 不跟随重定向，任何 3xx 均按失败处理，只接受 2xx；401 与 403 报密钥无效，429 报额度用尽。
- 不存储 Cookie，不发送 Windows 凭据，不做自动解压。
- 每次请求的连接、响应头与正文合计 8 秒超时。
- 边读取边统计字节，响应超过 5 MB 立即断开；`Content-Type` 必须是 `audio/*` 或 `application/octet-stream`；
  内容必须能解析为 RIFF/WAVE 16 位 PCM，否则丢弃且不写入缓存。
- 同一时刻只发出一个请求，排队最多 3 条；超出部分直接报失败，桌面端改用本机语音播报。
- 任何失败都只转换为一个错误码（`ERR_SPEECH_*`，见 contracts/error-codes.md），响应正文不回显给桌面端。
  桌面端改用本机语音播报同一文字，并只提示一次。

**附带流量。** 与 §8.2 相同：DNS 解析语音服务的主机名；遵循系统代理设置时可能有代理自动发现（WPAD / PAC）；

**只有采集服务联网。** 请求由采集服务发出，桌面端仍然禁止 `QNetworkAccessManager`（`NET-006`）。

**关闭方式。** 在设置「播报」中将语音引擎改回本机语音，或将服务改为"不使用"，之后不再发出任何请求。密钥可在同一处清除。

**总开关。** 环境变量 `MR_DISABLE_ONLINE_SPEECH=1` 使在线语音整体不可用。每次合成之前都会读取该变量，

**静态检查约束。** 见 §8.2 末段：`NET-006` 精确放行 `src/Collector/Speech/OnlineSpeechClient.cs`，
`NET-007` 限定 `tts.speech.microsoft.com` 只能出现在该文件中。OpenAI 兼容接口的地址由用户填写，仓库中没有对应的主机名可供检查；
守住该接口的是"只有该文件能发出请求"这一约束，以及上文对地址格式的校验。

### 8.4 更新检查：只读一次发布元数据（2026-09-17 起的放宽，默认开启）

**放宽理由。** 本软件依赖游戏协议，旧版本在游戏更新之后可能停止记录，修复只能随新版本发布，

**只读取一个文件。** 只读 `GET` 一个固定地址
`https://github.com/Harendotes-Tang/MentorRouletteRecorder/releases/latest/download/BUILD-METADATA.json`，

**请求不携带标识信息。** 请求没有查询串、没有 Cookie、没有安装 id、没有账号，也不发送 Windows 凭据；
除固定的 `User-Agent: MentorRecorder`（不带版本号）外不附加任何请求头。地址是固定的仓库路径，不含任何可变部分，
因此对端无从据此得知发出请求的是哪一个版本、哪一台机器。与任何网络连接一样，对端服务可以看到请求的来源 IP 地址与发生时间。
安装程序及其校验值的地址含有新版本的版本号，检查本身从不请求它们：只有用户点击「下载并安装」时，采集服务才请求这两个地址
（§8.6）；用户选择在浏览器中下载时，由系统浏览器请求安装程序的地址，与用户在发布页上自行点击下载相同。

**附带流量（重定向目标的 CDN 主机）。** `releases/latest/download/` 是一个重定向地址，
文件本身位于 `*.githubusercontent.com` 之下，具体主机名由 GitHub 决定，并会随时间变化。
因此本软件显式跟随该重定向，最多 3 跳，且每一跳都必须是 `github.com` 或 `*.githubusercontent.com` 上
默认端口的 `https` 地址。主机白名单按**后缀**匹配，正是因为 GitHub 会在不同的 `*.githubusercontent.com`
名字之间搬动发布资产，写死某一个主机名会使检查在下一次搬动后失效。§8.6 的下载不沿用这条规则，另有更窄的名单。
此外，以下流量与 §8.2 相同，由操作系统发起：DNS 解析上述主机名；遵循系统代理设置时，
Windows 可能执行代理自动发现（WPAD / PAC 脚本）；校验 TLS 证书时，Windows 可能访问证书机构（CRL / OCSP）。

**客户端行为限制。**

- 只接受 2xx，以及跳向上述白名单的重定向；超过 3 跳、跳向白名单之外的主机、跳向非 `https` 或非默认端口的地址，均按失败处理。
- 不存储 Cookie，不发送 Windows 凭据。
- 连接、重定向与读取合计 15 秒总预算。
- 边读取边统计字节，正文超过 16 KiB 立即断开。
- 只解析 `version` 一个字段。正文不是 JSON、缺少该字段，或版本号无法解析时按失败处理。
- 任何失败都**静默降级**：仓库尚未公开而返回 404、断网、被限流、正文不合法，界面上一律不出现任何内容，也不弹出任何提示。
- **检查不下载、不执行。**检查本身不取回安装包，不写入可执行文件；安装程序只在用户要求时下载（§8.6）。
  运行中的本软件从不替换自身的任何文件。

**不上传数据。** 该类请求只有一个 `GET`，没有请求正文；不发送本软件的版本号、设置、记录或任何本机信息。
请求由采集服务发出，桌面端继续禁止 `QNetworkAccessManager`（`NET-006`），发布页与浏览器下载时安装程序的地址一律交由系统浏览器打开。
检查结果经命名管道传给桌面端，即 `GetStatus` 应答中的可选对象 `update`（`enabled`、`update_available`、
`latest_version`、`release_url`、`installer_url`、`last_checked_at_utc`、`last_outcome`，以及 §8.6 的下载状态 `download`）；
「检查更新」对应的 `CheckUpdateNow` 与 §8.6 的两条消息在应答中给出同一个对象。
其中 `release_url` 即上文那个固定的公开发布页；`installer_url` 是 `latest_version` 所指版本的安装程序，即本项目发布资产
`https://github.com/Harendotes-Tang/MentorRouletteRecorder/releases/download/v<版本>/MentorRecorder-<版本>-setup.exe`，
与 `latest_version` 同时出现、同时缺席（`latest_version` 只能是三段纯数字的版本号）。`release_url` 与
`GetCalibrationShareCode.issue_url` 一样，只用于交给浏览器打开，采集服务从不请求它；`installer_url` 同样交给浏览器打开，
采集服务只在用户点击「下载并安装」时请求同一地址（§8.6）。
脱敏诊断报告中对应 `boundary.outbound.update_check`（`enabled`、`kill_switch`、`last_checked_utc`、
`last_outcome`、`latest_version`），其中不含主机名，也不含地址。

**总开关。** 环境变量 `MR_DISABLE_UPDATE_CHECK=1` 使检查完全不发生：不解析主机名，不建立连接；§8.6 的下载同样不发生。
任何非空且不为 `0` / `false` 的值同样生效，与 `MR_DISABLE_SHARED_FETCH` 一致。
`scripts/verify.ps1`、`scripts/test.ps1`、`scripts/package.ps1` 均设置该变量，因此验证、测试、打包期间不会联网。

**静态检查约束。** `NET-006` 的第三个例外是本节的 `src/Collector/Update/UpdateCheckClient.cs`，
同样按仓库相对路径精确匹配，不按文件名或目录名匹配。`NET-007` 为此增加 `github-content-hosts` 变体：
`githubusercontent` 除 §8.2 已放行的几处之外，还可以出现在该更新检查客户端中，此外任何位置都报错；
`jsdelivr` 仍只限于共享校准一侧，更新检查客户端中出现它同样报错。§8.6 的下载同样只经由该文件发出，没有增加任何放行。

### 8.5 安装程序下载 Npcap：仅在安装过程中、仅在缺少 Npcap 时

**为何由安装程序下载。** 本软件依赖 Npcap 读取网卡流量，而 Npcap 免费版的许可证不允许随本软件分发
（`THIRD_PARTY_NOTICES.md`）。为免去用户自行查找下载页的步骤，安装程序在本机没有 Npcap 时代为下载其官方安装程序。
这是发布物中唯一不经由采集服务的联网，也是 `NET-009` 唯一的放行（§2.1）。

**何时发生。** 只在运行安装程序的过程中。安装程序检查本机是否已有 Npcap（`%SystemRoot%\System32\Npcap\wpcap.dll`，
或注册表 `HKLM\SOFTWARE\Npcap` / `HKLM\SOFTWARE\WOW6432Node\Npcap`）；已有时不显示相关页面，也不发出任何请求。
没有时，向导先用一页说明原因，在「准备安装」页点击下一步后才开始下载。

**下载什么。** 只有一个文件：`https://npcap.com/dist/npcap-<版本>.exe`，版本号固定写在安装脚本
`installer/MentorRecorder.iss` 中。下载完成后由 Inno Setup 核对其 SHA-256 与脚本中登记的值一致，不一致即作废。
下载的是未经修改的官方安装程序，存放在安装程序自己的临时目录中，安装程序退出时随该目录一并删除。

**不静默安装。** 下载完成后启动该安装程序并显示其向导，由用户在 Npcap 自己的向导中选择选项、接受其许可条款并完成安装
（Npcap 免费版不提供静默安装）。下载失败时说明原因，本软件的安装照常继续；Npcap 仍未安装时，安装程序提示可随时到
`https://npcap.com` 自行安装，在此之前软件无法抓包。

**请求内容。** 请求由 Inno Setup 的下载组件发出，只是对上述固定地址的一次下载，不携带任何记录、设置或本机标识。
与任何网络连接一样，对端可以看到请求的来源 IP 地址与发生时间。

**运行中的软件不下载。** 安装完成后，采集服务与桌面端都不会下载或安装 Npcap：缺少 Npcap 时采集服务返回
`ERR_NPCAP_MISSING` 并给出安装指引（§6），桌面端可按用户的点击由系统浏览器打开 Npcap 官方站点。

### 8.6 按请求下载新版本的安装程序（2026-10-04 起的放宽，只在用户点击时）

**放宽理由。** §8.4 的检查只提示有新版本，下载与安装此前全部由用户在浏览器中完成：打开发布页、找到安装程序、
下载后自行运行。用户于 2026-10-04 决定在软件内完成这一步。本条有意放宽了本文件原先"本软件不下载安装包"的承诺，
放宽范围逐条列于下文。不变的是：**不点击就不下载，也不安装**；安装始终经过安装程序自己的向导，不静默安装。

**触发条件。** 只有用户的点击会发起下载：总览横幅、设置页"通用"与"关于"中的「下载并安装」，下载失败后的「重试」，
以及维护者工具中的「重新下载最新正式版」。每次点击由桌面端发出一条 `StartUpdateDownload`，采集服务立即应答，
下载在后台进行。下列情况下采集服务以 `FAILED` 应答，不发出任何请求：采集设置 `update_check_enabled` 关闭，
或设置了总开关 `MR_DISABLE_UPDATE_CHECK`（`DISABLED`）；尚未得知比本软件更新的版本（`NO_UPDATE`）。
「重新下载最新正式版」（`reinstall: true`）不要求该版本比本软件新，只要求已经得知。同一时刻只进行一次下载，
下载进行中再次请求只报告这一次的进度。上一次下载（包括已取消、仍在收尾的那一次）完全结束之前不开始新的下载，
两次开始之间至少相隔 5 秒；在此期间再次请求，采集服务原样报告当前状态，不发出任何请求，桌面端以一句提示
「没有开始下载，请稍候几秒再试。」说明，不当作下载失败。已就绪的安装程序在 5 秒内刚核对过时，再次请求直接报告就绪。要下载的版本就是 §8.4 读到的 `latest_version`，即发布页上最新的正式版，
只能是三段纯数字的版本号；先行版（测试包）不会被下载。

**只有两个请求。** 两个只读 `GET`，地址由固定的仓库路径与该版本号拼成：

1. 校验值 `https://github.com/Harendotes-Tang/MentorRouletteRecorder/releases/download/v<版本>/MentorRecorder-<版本>-setup.exe.sha256`，
   即与安装程序一同发布的 SHA-256（64 位十六进制、两个空格与文件名，由 `scripts/package.ps1` 生成）。
   只接受开头恰好 64 个十六进制字符、其后为结尾或空白的内容，其余一律视为没有校验值（`CHECKSUM_UNAVAILABLE`）；
2. 安装程序 `https://github.com/Harendotes-Tang/MentorRouletteRecorder/releases/download/v<版本>/MentorRecorder-<版本>-setup.exe`，
   即 §8.4 的 `installer_url`，边接收边写入磁盘。

校验值读不到时不请求安装程序。两个请求显式跟随重定向，最多 3 跳；途经的每一个地址，以及最终给出内容的地址，
都必须是默认端口、不带用户信息的 `https` 地址，并且只能是下列两种之一：

- `github.com` 上本项目该版本的发布目录 `/Harendotes-Tang/MentorRouletteRecorder/releases/download/v<版本>/` 之下、
  路径中不含转义字符（`%`）的地址；
- GitHub 存放发布资产的两个主机 `release-assets.githubusercontent.com` 与 `objects.githubusercontent.com`。

其他地址一律按失败处理（`HOST_REFUSED`）。这比 §8.4 的检查更窄：检查接受 `*.githubusercontent.com` 下的任何主机，
而其中有些主机上任何 GitHub 用户都能发布内容，下载的文件却会以管理员权限运行。GitHub 日后若改用其他主机存放发布资产，
下载会因此失败，此时仍可改用浏览器下载。两个请求都不存储 Cookie，不发送 Windows 凭据，不做自动解压。
重定向目标带有 GitHub 签发的查询串，日志与应答都不记录任何地址。

**限制。**

- 校验值：边读取边统计字节，超过 1 KiB 立即断开；连接、重定向与读取合计 15 秒，与 §8.4 的检查相同。
- 安装程序：声明的长度超过 300 MiB 时不读取，接收的字节超过 300 MiB 时立即放弃（`TOO_LARGE`）；
  30 秒没有收到任何数据（包括等待该请求的应答）即放弃（`TIMEOUT`）；整个下载（含校验值）最长 30 分钟。
  连接在声明的长度之前结束时，文件不完整，按失败处理。
- 任何失败都以一句中文说明告知用户发生了什么、可以怎么做（重试，或「在浏览器中下载」），不显示内部名称或地址。

**发送的内容。** 两个请求的地址都不带查询串（重定向目标中的签名查询串由 GitHub 给出），也没有请求正文、Cookie、安装 id 或账号；
除固定的 `User-Agent: MentorRecorder`（不带版本号）外不附加任何请求头。地址中只有固定的仓库路径与公开的版本号，
不含任何能认出用户或本机的信息。与任何网络连接一样，GitHub 及其 CDN 可以看到请求的来源 IP 地址与发生时间，
并可由地址得知被下载的是哪一个版本。附带流量（DNS 解析、代理自动发现、证书吊销检查）与 §8.4 相同。

**写入的内容。** 只写入数据目录（数据库所在的文件夹，默认 `%LOCALAPPDATA%\MentorRecorder\`，或 `MR_DATA_DIR` 指向的目录）
下的 `updates\`：

- 下载中写入 `updates\MentorRecorder-<版本>-setup.exe.part`。该文件以独占方式新建：同名的旧条目先作为目录项删除，
  放在那里的链接因此不会被沿用。写入的同时计算 SHA-256；写完后刷新到磁盘，与公布的校验值比较，一致才改名为
  `updates\MentorRecorder-<版本>-setup.exe`。改名之后再以不允许他人写入的方式打开这个文件，重新计算一次 SHA-256，
  仍与公布的值一致才报告就绪（`READY`）；不一致（`CHECKSUM_MISMATCH`）或无法这样读取（`DISK_FAILED`）时删除该文件。
  任何一步不一致、任何失败与用户点击「取消」都删除 `.part`，不保留任何不完整或未经核对的文件。
- 文件名只由版本号拼成，不取自服务器返回的任何内容。`updates` 不存在时创建；它是文件或链接（联接点、符号链接等重解析点）时
  拒绝写入（`DISK_FAILED`），不经由它写入或删除任何内容。任何请求都在确认该文件夹可用之后才发出。
  采集服务在其中工作期间（一次下载的全程，以及每一次清理、删除与计算校验值）以不允许删除的方式打开该文件夹本身，
  不经由链接；在此期间它与它的上级文件夹都不能被改名、删除或替换为链接。
- 清理只按本软件自己的文件名进行，只处理直接位于 `updates\` 中的普通文件，不跟随链接，不触及其他任何内容：
  每次开始下载时删除其中本软件留下的 `.part` 与各版本的安装程序；采集服务每次启动时删除 `.part`，以及除仍比本软件新的
  最新版本之外的全部安装程序（更新检查关闭时全部删除），因此安装完成后的下一次启动会删去已用过的安装程序。
  正被占用而删不掉的文件留待下次。关闭「检查新版本并提示」时，已就绪的安装程序立即删除（见下文"关闭方式"）；
  已就绪之后再次点击却被拒绝（更新检查已关闭，或已没有更新的版本）时，该安装程序同样删除。
- 采集服务停止时取消进行中的下载，最多等待 5 秒，使它删去 `.part` 之后再退出。

**两次核对。**

- 采集服务：如上所述，写入的内容与改名后保留的文件都要与公布的 SHA-256 一致，才以 `READY` 报告文件路径与校验值。
  再次请求一个已就绪的版本时，采集服务重新计算一次（`VERIFYING`），文件仍一致才再次报告 `READY`，否则重新下载；
  上一次核对不到 5 秒时直接报告 `READY`。
- 桌面端：用户点击「立即安装」时，桌面端在启动任何程序之前先按报告的路径核对：它是绝对路径，所在文件夹恰为数据目录下的
  `updates`，文件名恰为所报告版本的 `MentorRecorder-<版本>-setup.exe`；它是普通文件，文件本身与所在文件夹都不是链接
  （符号链接、联接点、快捷方式或其他重解析点）。随后桌面端以读取方式打开该文件，只允许其他程序读取它，路径末端若是链接
  则打开链接本身而不跟随；有程序正以写入方式打开它时无法这样打开，这次安装随即放弃。从打开起，直到安装程序已经启动、
  本软件退出，或这次安装被放弃，桌面端始终持有这个文件：期间任何程序都不能写入、改名或删除它，也不能改名它的上级文件夹，
  因此被启动的正是核对过校验值的那个文件。普通文件与位置两项核对在打开的文件上再做一次：它必须是磁盘上的普通文件，
  系统为它解析出的完整路径（沿途的链接全部展开）必须与报告的路径一致（只忽略字母大小写）。SHA-256 通过同一次打开读取、
  当场计算，必须等于采集服务报告的值。任何一项不符都不启动，桌面端随即释放该文件，以一句说明告知用户，
  同时提供「在浏览器中下载」。数据目录经由链接（联接点、符号链接）、SUBST 映射的盘符或映射的网络驱动器到达时，
  解析出的路径与报告的路径不同，「立即安装」因此不启动安装程序，并说明无法确认它位于本软件的数据目录中；浏览器下载仍然可用。

**由谁启动、何时启动。** 采集服务从不执行它下载的文件。只有用户点击「立即安装」、上述核对全部通过，并且此时没有正在进行的导随
（已匹配或已进入副本；尚未读到当前导随状态时同样不安装）时，桌面端才经系统外壳打开该文件，与在资源管理器中双击它相同。
是否在导随中，在计算校验值之后、启动之前再确认一次。启动时文件仍由桌面端持有，持有只禁止写入、改名与删除，不妨碍读取与启动。
安装程序要求管理员权限，Windows 因此弹出管理员批准提示。启动成功后，桌面端经正常的退出路径关闭（先请求采集服务正常停止，
见 §4.2"退出路径"），退出时才释放该文件，由安装程序的向导完成更新：替换本软件文件的是用户启动的安装程序，
而不是运行中的本软件。启动没有成功时（例如用户在批准提示中选择了「否」），桌面端立即释放该文件，本软件继续运行并说明原因。

**校验值能防什么、不能防什么。** 校验值与安装程序发布在同一个发布页上。它能发现传输中或磁盘上的损坏、不完整的下载，
以及文件被混淆或替换为另一个文件；它**不能**防范能够向本项目发布页上传资产的一方，这一方可以同时替换安装程序与校验值。
安装程序没有代码签名。这是已知的限制：软件内下载的可信程度与用户在浏览器中从同一发布页下载相同，并不更高。
此外，系统外壳按用户自己的设置决定由哪个程序处理 `.exe` 文件，以同一用户身份运行的其他程序可能事先改动这一设置；
与未签名的安装程序和同源的校验值一样，这超出了本软件能够核对的范围。

**关闭方式。** 关闭设置页"通用"中的「检查新版本并提示」，或设置环境变量 `MR_DISABLE_UPDATE_CHECK=1`
（任何非空且不为 `0` / `false` 的值同样生效）后，检查与下载都不再发生：`StartUpdateDownload` 以 `DISABLED` 应答，
不解析主机名，不建立连接。关闭「检查新版本并提示」的那一刻，正在进行的下载随即停止，已写入的部分删除，已就绪的安装程序
也随之删除，下载状态改为失败，并以一句说明告知用户下载已停止、安装程序不再提供；此前运行中留下的安装程序在采集服务下次启动时删除。
用户仍可在浏览器中自行从发布页下载安装程序；界面仍显示此前查到的新版本时，可点「在浏览器中下载」。
`scripts/verify.ps1`、`scripts/test.ps1`、`scripts/package.ps1` 均设置该变量，下载相关的测试使用不联网的替身传输层。

**本机记录。** 采集服务的诊断日志（组件 `update`）对每次下载只写两行：开始时记版本号，结束时记结果、字节数与耗时，不含地址。
下载状态经命名管道以 `UpdateStatus.download` 报告（`state`、`version`、`received_bytes`、`total_bytes`，
就绪时另有 `file_path` 与 `sha256`，失败时另有 `failure` 与 `message`），消息为 `StartUpdateDownload` 与 `CancelUpdateDownload`
（`contracts/ipc-v1.schema.json`）。脱敏诊断报告不包含下载的任何内容。

**网络代码仍只在一个文件中。** 两个请求都经由 §8.4 的 `src/Collector/Update/UpdateCheckClient.cs` 发出，
该文件仍是更新一侧唯一允许出现 HTTP 客户端（`NET-006`）与 `githubusercontent`（`NET-007`）的地方，静态检查没有为下载增加任何放行；
下载的状态、写盘与核对都在 `src/Collector/Update/` 的其他文件中，只经由该文件联网。桌面端继续禁止 `QNetworkAccessManager`（`NET-006`）
与自行下载（`NET-009`）：它只发出 `StartUpdateDownload` / `CancelUpdateDownload`，下载进行中约每秒重读一次 `GetStatus` 以显示进度，
并在安装前持有并读取本机文件计算校验值。

## 9. 用户可自行验证的方式

用户可通过以下方式核对上述声明：

1. 用 `netstat -ano` 检查本软件的进程没有任何 LISTENING 端口。桌面端进程在任何时候都不应有出站连接。
   采集服务只在三种情况下短暂连出：其一是 §8.2 所列条件下连向那几个源的 443 端口，对端地址属于 GitHub 与 jsDelivr 的 CDN；
   其二是用户开启在线语音之后，播报或点击「测试」时连向用户选定的语音服务（§8.3；Azure 为 `<区域>.tts.speech.microsoft.com` 的 443 端口，
   OpenAI 兼容接口为用户填写的地址）；其三是更新：桌面端处于连接状态时的更新检查（§8.4），每 24 小时最多一次，
   以及用户点击「下载并安装」之后对安装程序及其校验值的下载（§8.6），都连向 `github.com` 的 443 端口，
   并跟随其重定向连向其他主机的 443 端口：检查为 `*.githubusercontent.com` 下的主机，下载只能是
   `release-assets.githubusercontent.com` 或 `objects.githubusercontent.com`；下载持续到安装程序接收完毕，
   或失败、被取消、「检查新版本并提示」被关闭为止。
   在设置中关闭「游戏更新后获取其他玩家的共享校准」与「检查新版本并提示」、并将播报的语音引擎保持为本机语音，
   或设置 `MR_DISABLE_SHARED_FETCH=1`、`MR_DISABLE_ONLINE_SPEECH=1` 与 `MR_DISABLE_UPDATE_CHECK=1` 并重启软件之后，
   两个进程都不应出现任何出站连接。
   「分享给其他玩家」与「查看更新说明」打开的网页、「在浏览器中下载」（或「下载新版本」）交给浏览器的下载都属于系统浏览器进程，
   不计入其中；安装时下载 Npcap 的是安装程序（§8.5），「立即安装」启动的也是安装程序，同样不属于这两个进程。
2. 用 Process Explorer 检查本软件没有打开游戏进程的句柄：选中 `MentorRecorder.Collector.exe`，打开下方的句柄视图
   （View → Lower Pane View → Handles），类型为 Process 的条目中不应出现 `ffxiv_dx11.exe` 或 `ffxiv.exe`；
   对 `MentorRecorder.Desktop.exe` 做同样的检查。采集服务的句柄中可能有一条指向 `MentorRecorder.Desktop.exe`，
   那是父进程看门狗（§2.1），不是游戏。游戏客户端由启动器以管理员身份拉起时，这一检查同样适用：
   读取进程编号、启动时间与路径用的是内核进程表（§2 第 3b 条），不需要也不会打开游戏进程。
3. 检查安装目录中**没有** `deucalion-*.dll`。安装目录中唯一由本软件在运行时写入的内容是
   `note-images\`（或 `MR_NOTE_IMAGE_DIR` 指向的目录）：用户在备注里附上的图片，按记录编号分文件夹，
   由桌面端复制自用户自己选择的文件；不经过采集服务，不进入数据库、日志、诊断报告、导出与备份，
   可整体删除（对应记录的图片随之消失，记录本身不受影响）。
4. 检查 `%LOCALAPPDATA%\MentorRecorder\`（或 `MR_DATA_DIR` 指向的目录）中**没有**
   `.pcap` / `.pcapng` 文件。该目录下只会出现下列内容，每一项均可删除：

   | `tts-cache\` | 仅在使用过在线语音之后（§8.3；默认关闭） | 在线语音取回的读音 `<sha256>.wav`，每个文件对应一条播报的声音，可能含副本名与进度数字；上限 20 MB，按最近使用淘汰 | 下次播报同一文字时重新请求一次 |

   | `updates\` | 仅在用户点击过「下载并安装」之后（§8.6） | 下载中的 `MentorRecorder-<版本>-setup.exe.part` 与核对通过的 `MentorRecorder-<版本>-setup.exe`；每次开始下载时删除本软件此前留下的 `.part` 与安装程序，采集服务每次启动时删除 `.part` 与已不再提供的版本的安装程序 | 已下载的安装程序随之删除，需要时重新下载 |

   **信任边界的变化。** 该目录对用户可写，而其中的 VERIFIED 档案会驱动记录。因此，
   随包目录中存在同版本、可用的档案时，本机校准档案自动让位，唯一的例外是随包档案只能按排本推断匹配、
   而本机档案认得出服务器的匹配报文（[protocol-profile-format.md](protocol-profile-format.md) §11.2 的目录合并规则）；
   界面常驻"本机校准"标签；诊断报告与 `capture_sessions`
   记录其 id（`profile_origin = LOCAL_CALIBRATION`），事后可以找出由它产生的每一条记录。

   共享档案同样会驱动记录，因此门槛更高。下载的校准码先在本机流量中按结构核实，通过后才写出档案（门槛见 §8.2）；
   同一版本另有可用档案时，先看谁认得出服务器的匹配报文，再按随包、本机、共享的顺序选取。
   共享档案有独立的目录，界面标签为「共享校准」，记录中为 `profile_origin = SHARED_CALIBRATION`。
   `shared-calibrations\` 中的校准码本身不是档案，档案目录不读取它。
