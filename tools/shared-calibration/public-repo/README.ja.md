# MentorRecorder 共有キャリブレーション

[简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md)

このリポジトリには、「导随记录器」（MentorRecorder）のプレイヤーが共有する**キャリブレーションコード**を保存しています。

ゲームのアップデートでは、メッセージ番号（opcode）が変更される場合があります。同じリージョン・同じクライアントバージョンの番号はゲームクライアントに組み込まれており、すべてのプレイヤーで共通です。
そのため、あるプレイヤーがソフトウェア上でキャリブレーションに成功すれば、その結果を共有でき、ほかのプレイヤーが一人ずつやり直す必要はありません。

## 実行場所とデプロイ

現在、提出の自動受け付け、隔離、復帰、候補の保存は、**GitHub Actions 上の Python ルール**で実行しています。大規模言語モデル、モデル API キー、メンテナーの常時稼働 PC は必要ありません。
プレイヤーの PC がローカルで証拠を収集・検証し、本人が提出を確定した後に限り、プレビューした要約が GitHub に送られます。正式な記録機能と Npcap によるパケットキャプチャは、引き続き Windows 版レコーダーの機能です。
このリポジトリの Python スクリプトによって、レコーダーが macOS 用のゲームデータ収集クライアントになるわけではありません。

Mac mini は、別途設定すればローカルでの研究やモデルによる補助処理に使えますが、このリポジトリには**ローカル・クラウドのどちらの大規模言語モデルも接続されておらず、セルフホストランナーも設定されていません**。
現在の運用では、Mac mini を起動しておく必要はありません。モデルは、キャリブレーションコードや要約だけから未知のリージョンの実際のプロトコルを補完したり、ローカル検証を代替したりすることはできません。

## 旧クライアントとの互換性

新しいリポジトリでも、`index.json` の `schema_version: 1`、`MRC1.` 形式、キャリブレーションコードのパス、従来の提出フォームを維持しています。
共有キャリブレーション機能がある旧クライアント（公開済みの `v1.7.2` を含む）は、引き続きインデックスを読み込み、自身のリージョン、ゲームバージョン、同梱テンプレートに一致するコードをダウンロード・検証できます。
共有キャリブレーションに対応していない、さらに古いクライアントに、このリポジトリの更新だけで機能が追加されることはありません。テンプレートが一致しない場合やゲームバージョンが未対応の場合も、従来のルールに従って使用を拒否します。

| 機能 | 共有キャリブレーション機能がある旧クライアント | 新しい証拠提出フローに対応するクライアント |
|---|---|---|
| 従来のインデックスフィールドと `MRC1.` コードの読み込み | 互換性を維持 | 対応 |
| 従来のフォームによるコード提出 | 互換性を維持 | 対応 |
| リポジトリの可逆的な隔離と完全検証の制限 | `quarantined` / `quarantine_epoch` を無視し、従来のルールを使用 | 新しい制限を適用。ただしローカルで十分に検証済みのプロファイルは維持 |
| 最小限の証拠のプレビュー・提出、テンプレートがないリージョンでの収集ガイド | 新しい操作項目なし | 対応するクライアントと収集サービスの両方を更新する必要あり |
| 正式なテンプレートがない新リージョンへの自動対応 | 非対応 | 同様に非対応。まず候補となる手がかりを収集 |

**読み込みの互換性があっても、新しいルールが旧ソフトウェアに適用されるわけではありません。** 自動隔離を永久的な `revoked` に見せかけて、旧ソフトウェアに使用停止を強制することはありません。
今回の証拠関連機能はソースコードには実装済みですが、ソフトウェアのインストールパッケージとしてはまだ公開していません。このリポジトリの更新や新しい README の閲覧だけで、インストール済みのクライアントに新しい操作項目や隔離時の条件が追加されることはありません。

## ソフトウェアによるこのリポジトリの利用方法

- **読み取り専用のダウンロード。** ゲームの更新後に使用可能なローカルプロファイルがない場合、ソフトウェアは `index.json` を読み込み、同じリージョン・同じクライアントバージョンのコードファイルをコミット ID を指定してダウンロードします。
  使用中のプロファイルが共有コード由来で、まだ完全に検証されていない場合、またはコンテンツ申請からマッチングを推測している場合は、同じ最短間隔（6 時間に最大 1 回）でインデックスを再読み込みし、取り消しや、より適切なコードの有無を確認します。
  ソフトウェアがここへ何かをアップロードすることはありません。
- **検証してから使用。** ダウンロードしたコード自体はプロファイルではありません。まずプレイヤーのローカルトラフィックで構造を検証し、少なくともログイン時のゾーン変更メッセージが検証に合格してから、プロファイルを生成して記録を開始します。
  記録開始後も、コンテンツ申請と突入のメッセージを引き続き検証します。検証に合格しなければローカルでのキャリブレーションを続け、すでに得られた証拠は保持します。
  誤ったコードは、それが検出されるまでの間に、記録の欠落や誤記録を生じさせる可能性があります。ローカルトラフィックとの矛盾を検出した後は使用を停止し、そのコードから生成した記録を要再確認として扱います。
- **無効化可能。** 共有キャリブレーションの取得は、ソフトウェアが標準で有効にする 2 種類の外向きリクエストの一つです。もう一つは新バージョンの確認で、メインプロジェクトのリリースページにあるバージョン情報ファイルを読み込みます。このリポジトリとは無関係です。
  どちらも設定で無効化できます。このほかに、プレイヤー自身が有効にするオンライン音声機能がありますが、標準では無効で、こちらもこのリポジトリとは無関係です。
  リクエストの送信時機、送信内容、無効化方法は、ソフトウェアのプライバシーに関する説明に記載しています。

## コードに含まれる情報・含まれない情報

キャリブレーションコードは、`MRC1.` に、圧縮した正規化 JSON を続けたものです。

| 含まれる情報 | 含まれない情報 |
|---|---|
| 形式バージョン、リージョン（`CN` / `GLOBAL`）、クライアントバージョン | キャラクター名、サーバー、アカウント、IP アドレス |
| 使用する同梱テンプレートの ID とハッシュ | タイムスタンプ、サンプル数、申請したルーレットの種類 |
| マッチングの検出方式と、それに必要なメッセージ長、バイトオフセット、状態値 | 説明文、ファイルパス、メッセージ本文 |
| 学習したメッセージ番号（マッチング通知、ゾーン変更、コンテンツ、ジョブ） | |

コードの識別子 `code_sha256` は正規化内容の SHA-256 で、リポジトリ内のファイル名には先頭 12 桁を使います。

## 提出方法

ソフトウェア上でキャリブレーションに成功し、キャリブレーションのタイムラインを確認したら、「ほかのプレイヤーに共有」（「分享给其他玩家」）をクリックします。このボタンには対応するソフトウェアバージョンが必要です。ブラウザーで、このリポジトリの入力済み Issue ページが開きます。
「这份校准码的来源」欄には「本机校准得到，并逐条核对过校准时间线」（ローカルでキャリブレーションし、タイムラインを項目ごとに確認済み）が入力されています。確認欄にチェックを入れて提出すると、GitHub Action が自動検証・公開し、
Issue に結果を返信してクローズします。通常、メンテナーの対応は必要ありません。

ほかのプレイヤーが共有したコードを使用している場合、ソフトウェアがローカルでの検証に合格し、1 回のコンテンツを最後まで記録すると、「このキャリブレーションが使えたことを伝える」（「这份校准好用，告诉其他玩家」）が表示され、同じフォームを開けます。
この場合、出所欄には「其他玩家分享，已在我的软件里核实通过并正常记录」（ほかのプレイヤーによる共有で、自分のソフトウェアでも検証に合格し正常に記録済み）が入力されます。同じコードの提出は提出者数に加算され、ほかのプレイヤーのソフトウェアがそのコードを優先的に利用するために使われます。

出所欄はソフトウェアが入力するため、変更しないでください。別の内容に変更した提出は拒否されます。欄が空の場合（代理提出や、この欄に未対応のソフトウェアからの提出など）は、ローカルでキャリブレーションしたものとして扱います。

GitHub アカウントがないプレイヤーは、ソフトウェアでコピーしたコードをほかの人に代理提出してもらえます。以下のルールは代理提出者のアカウントに対して適用されます。

## 受け付けルール

- 提出する GitHub アカウントは、**登録から 30 日以上**経過している必要があります。
- コード内のクライアントバージョンは、`2026.09.01.0000.0000` のようなゲームクライアントのバージョン形式である必要があります。
  日付は、提出日（UTC）の翌日を超えてはいけません。
- **各 GitHub アカウントは、リージョンとクライアントバージョンの組み合わせごとに、同時に一つの有効なコードのみを保持できます。** アカウントの数値 ID を使って管理するため、名前を変更しても枠は増えません。
  同じコードを再提出しても重複加算されません。別のコードを提出すると、前のコードを**置き換えます**。詳しくは次の節を参照してください。
- **各アカウントの提出回数には上限があります。** 同じリージョンとクライアントバージョンでは、異なるコードを累計 3 件まで提出できます。また、1 日に提出できるリージョンとクライアントバージョンの組み合わせは 2 件までです。
  日付は UTC で計算します（中国標準時では毎日 8:00 に新しい日が始まります）。共有キャリブレーションを有効にした各ソフトウェアがインデックスをダウンロードし、そのサイズには上限があるため、この二つの制限によって一つのアカウントによる容量の占有を防ぎます。
- 提出したコードをメンテナーが取り消した場合、そのアカウントからの、そのリージョンとクライアントバージョンに対する提出は、メンテナーが再確認するまで**受け付け停止**になります。「取り消し」を参照してください。
- **提出者数の上限はありません。** 異なるアカウントがまったく同じコードを提出した場合は、一つのエントリにまとめます。`submitters` は、そのコードを提出、または検証済みとして報告した異なるアカウント数です。
  ローカルで得たコードと、「ほかのプレイヤーから共有され、自分の環境でも検証済み」のコードには、同じルールを適用し、同様に数えます。
  ソフトウェアは提出者数が多い順にダウンロード・検証します。同数の場合、`conflicting` のないものを優先し、次に前バージョンと構造が一致するもの（構造に関する事前情報を表す `shape_prior` が `true` のもの）、
  その後は公開順に選びます。「コード同士が一致しない場合」を参照してください。一つのバージョンで同時に検証するコードは最大 8 件です。
- コードは、`templates/` の同梱テンプレートを使って構造を再構築できる必要があります。形式の誤り、テンプレートの不一致、不正な構造がある提出はすべて拒否し、Issue に理由を記載します。
- 拒否した Issue はクローズします。修正後は新しい Issue を提出してください。クローズ済みの Issue を編集しても再処理されません。

## 自分が提出したコードの訂正

提出したコードに誤りがあると分かった場合や、その後より適切なコードを取得できた場合も、**メンテナーへの連絡は不要**です。ソフトウェアで再び「分享给其他玩家」をクリックし、
通常どおり新しい Issue を提出してください。Action が、そのリージョンとバージョンに対する以前の提出を新しいコードで置き換え、返信で説明します。

- 以前のコードの提出者が自分だけだった場合、そのコードは取り消されます（`revoked: true`。エントリは保持）。ほかのプレイヤーのソフトウェアは使用しなくなります。
- 以前のコードをほかのアカウントも提出していた場合、コード自体は残り、自分の提出分だけが除かれます。`submitters` も一つ減ります。
- 一度取り消したコードは再公開しないため、再提出しても公開状態には戻りません。新しいコードを提出してください。
- この置き換えによる取り消しは、以後の提出に影響しません。ただし、コードが**メンテナーによって**取り消された場合は、そのリージョンとバージョンへの提出が、
  メンテナーによる再確認と解除まで停止します。取り消しが誤りだと思う場合は、Action が受け付けを拒否した Issue にコメントしてください。

## コード同士が一致しない場合

同じリージョン・同じクライアントバージョンに複数のコードがある場合、Action は公開、提出者数への加算、取り消しのたびに比較し直し、`index.json` のエントリに二つの任意フィールドを記録します。
旧ソフトウェアはこれらを無視し、従来どおりの順序で選択できます。

- **`conflicting`。** コードをフィールドごとに比較します。対象はゾーン変更、エリア、ジョブ、マッチングの各メッセージです。マッチングについては、検出方式と、それに対応する長さ、オフセット、状態値も比較します。
  最初の三つは検出方式にかかわらず比較し、マッチングメッセージは同じ検出方式の範囲でのみ比較します。コードにないフィールドは比較しません。同じバージョン・同じテンプレートの別の未取り消しコードと、
  一つでも異なるフィールドがあれば、両方を `conflicting: true` とします。この印は差異があることだけを示し、どちらが誤りかを断定するものではありません。提出者数が同じ場合、ソフトウェアは、自分の環境で前バージョンに検証済みのプロファイルと、マッチングメッセージの構造が一致するコードを優先します。
  そのような根拠がない場合は、どちらもプレイヤーの PC で完全に検証してから有効にします。一方のコードの提出者や検証済みの報告者が増えれば、その状況に応じて判断します。
- **`shape_prior`（構造に関する事前情報）。** 同じリージョン・同じ検出方式について、コードが存在する直前のバージョンと比較します。マッチングメッセージの構造（長さ、ルーレットのオフセット、状態値）が
  一致すれば `true`、直前のバージョンにコードがあるものの、いずれとも構造が一致しなければ `false`、比較できる直前バージョンがなければ記録しません。現在のバージョンにコードを提出したアカウントについては、
  そのアカウントが過去のバージョンに提出したコードをこの比較から除外します。これにより、自作のバージョン番号を使い、自分のコードの事前情報を作ることはできません。
  このフィールドが決めるのはダウンロード・検証の順序だけです。コードの有効化に際して比較するのは、PC 自身が前バージョンに検証したプロファイルであり、このフィールドではありません。
  また、この値を拒否の根拠には使いません。ゲーム側が実際に構造を変更した場合、構造が以前と同じコードのほうが誤っている可能性もあるため、どちらもローカルでの検証が必要です。

差異が見つかった場合、Action は新しい提出 Issue への返信で、どの Issue のコードと、どのフィールドが異なるかを説明します。相手側の Issue にも 1 回コメントします（新しいコードの公開時のみ。同じコードに提出者が増えても繰り返しません）。
双方の Issue に `conflicting` ラベルを付けるため、メンテナーはラベルから確認できます。返信では差異だけを記載し、正誤は判定しません。
自分のコードが正しいと確認できていれば、追加の対応は不要です。誤りだと分かった場合は、ソフトウェアから改めて共有すれば置き換えられます。

## コードの競合をどう裁定するか

日常の裁定は、**ソフトウェアのローカル検証と、リポジトリの固定ルール**で行います。メンテナーがほかのリージョンのゲームをインストールしたり、各事例を再現したりする必要はありません。プレイヤーは最小限の要約をソフトウェアでプレビューし、
自分の操作で提出します。リポジトリは自動で検証・重複排除し、各アカウントの最新の立場を記録します。証拠が不足していれば自動的に待機します。バックグラウンドアップロードや大規模言語モデルは使いません。

### 自動隔離と復帰

- [共有キャリブレーション証拠フォーム](../../issues/new?template=evidence-calibration.yml)を使います。受け付けるのは `calibration-evidence-v1` のみです。
  公開形式の唯一の定義は `schemas/calibration-evidence-v1.schema.json` にあります。不明なフィールド、非公開であるべき情報のフィールド、JSON キーの重複、上限超過、不正な数値は拒否します。
- 身元情報には、GitHub がその時点で返すアカウントの数値 ID を使います。登録から 30 日以上のアカウントだけを票として数えます。同じリージョン、ゲームバージョン、テンプレート、コード、ルールバージョン、フィールドの範囲で、
  各アカウントの最新の完全かつ有効な 1 票だけを保持します。異なる二つ以上の、完了済みかつ正常なセッションで、同じフィールドに同じ結論が得られた場合のみ票になります。重複する要約・セッション、古い Issue の編集、失敗した処理の再試行では票は増えません。
  まだ票になっていない待機中の要約は、実際の二つのセッションがそろうまで補完できます。一つの Issue でいずれかのフィールドが票として成立した時点で、その Issue は固定されます。その後の新しい立場や別のフィールドは、ソフトウェアから新しい証拠 Issue を作成してください。
- 同じフィールドで、少なくとも **3 アカウント × 各 2 回の正常なセッション**が明確な矛盾を示し、否定側のアカウント数が肯定側を上回ると、自動で `quarantined` を設定し、`quarantine_epoch` を増やします。
  新しいソフトウェアはそのコードのダウンロードと観察を続けますが、完全検証を終えるまで直接有効化できません。すでにローカルで完全に検証したプロファイルは、リモートでの隔離だけを理由に取り下げません。
- 自動復帰するには、隔離理由ごとに、**今回の隔離後に新しく受け付けた**、現在の epoch に属する同規模の肯定的証拠が必要です。さらに、肯定側のアカウント数が否定側を上回る必要があります。
  復帰後、前の回の否定的証拠によって直ちに再隔離することはありません。古いセッションを包み直しても、復帰用の新しい証拠にはなりません。
- 自動隔離は `revoked` を設定せず、コードを削除せず、アカウントを凍結しません。複数の候補を共存させられます。永久取り消しは、後述する独立した保守操作として残しており、通常の報告を理由にシステムが実行することはありません。

**件数と形式は処理上の条件であり、提出者が実際にゲームをプレイしたこと、内容が真実であること、アカウント同士が独立していることを証明しません。** ソフトウェアの最終判断には、引き続きローカルでの完全検証を使います。
旧ソフトウェアは隔離フィールドを無視し、従来のローカルルールで動作します。このリポジトリの更新だけで旧ソフトウェアに新しい条件は追加されません。
リポジトリへのすべての書き込みは、共通の公開処理用同時実行ロックを使います。プッシュが競合した場合は、最新の `main` から再計算します。自動返信は Issue ごとに一つのボットコメントとし、再試行では追記せず更新します。
定期 sweep は永続カーソルを使い、取りこぼしたイベントを分割して補処理します。台帳には容量上限があり、到達すると自動的に待機します。リプレイ防止記録を削除して、古い証拠を新しいものとして扱うことはありません。
現在の全体上限は、要約 4096 件、セッションのランダムな別名 32768 件、最新のフィールド別立場 16384 件、台帳 8 MiB です。通常の文章による報告の受領記録は別に最大 4096 件保持します。
アカウントごとの上限は、要約 128 件、セッションの別名 1024 件、文章による報告 64 件です。超過時は新しい記録枠を消費せず `ACCOUNT_CAPACITY_WAIT` を返します。アカウントを凍結したり、既存の票を変更したりはしません。
全体容量が尽きた場合は `LEDGER_CAPACITY_WAIT` を返します。無制限の履歴や、上限到達後の新規受け付けを保証するものではなく、容量を空けるためにリプレイ防止記録を自動破棄することもありません。

### ソフトウェアによる差異の扱い

フィールド単位の合意とローカルの事前情報を使うには、これらの仕組みに対応するソフトウェアバージョンが必要です。このリポジトリだけを更新しても、旧ソフトウェアに機能は追加されず、旧バージョン自身の検証ルールで候補を処理します。
対応するバージョンでは、同じリージョン、クライアントバージョン、テンプレートの候補を次のルールで扱います。

- **フィールドごとに集計。** ゾーン変更、エリア、ジョブを個別に比較し、マッチングメッセージは同じ検出方式の中だけで比較します。宣言されていないフィールドは投票対象にしません。
  各フィールドで、同じ値を支持するコードの `submitters` を合算します。あるコードが、差異のあるすべてのフィールドで裁定根拠を持つ必要があります。一つのフィールドの票が多いだけで、残りを省略することはありません。
- **票数が影響するのは優先順位と検証条件だけ。** ほかの値より多い票は合意の根拠になりますが、正しさが証明されたことは意味しません。票が少ないコードを、その理由だけでリポジトリが取り消したり、ソフトウェアが永久に拒否したりすることはありません。
  実際に有効化するには、使用するソフトウェアバージョンのほかの前提条件を満たし、ローカルトラフィックによる検証に合格する必要があります。
- **同票では安易に片方を選ばない。** マッチングメッセージのフィールドが同票の場合に限り、この PC が前バージョンで検証済みのプロファイルの構造を使って裁定できます。
  一方だけがローカルの事前情報に一致し、同票のほかの候補には根拠がない場合のみ、同票を解消できます。ほかのフィールドの同票、双方に根拠がある場合、新規インストールで過去のプロファイルがない場合は、事前情報では裁定しません。
  リポジトリの `shape_prior` はダウンロードと検証の順序にだけ使い、ローカルの証拠を代替しません。
- **裁定できなければ完全検証。** 十分な合意やローカルの事前情報がない候補は、必要なコンテンツ申請、マッチング、突入などをローカルで検証し終えてから有効化します。
  動作中に矛盾を判定した場合は、その候補を無効にし、ソフトウェア自身のルールに従って、別の候補の試行またはキャリブレーションを続けます。別々のコードのフィールドを組み合わせ、誰もキャリブレーションしていない「合意コード」を作ることはありません。

例えば、MARKER_OFFSET 方式の二つのコードがそれぞれ 1 人の提出者を持ち、ゾーン変更、エリア、ジョブは一致し、マッチングメッセージの長さだけが 24 バイトと 40 バイトに分かれているとします。
最初の三つのフィールドに差異はなく、マッチングフィールドは 1 対 1 です。ローカルで前バージョンに検証した構造が一方だけを支持する場合は、それを使ってこの PC 上の同票を解消できます。
そのローカルの根拠がなければ、両方とも先に完全検証します。リポジトリは、24 バイトの構造が一般的というだけで 40 バイトのコードを取り消すことはできません。

### 任意の手動確認と永久取り消し

1. **候補の特定。** `conflicting` ラベルのある提出 Issue、または「报告校准有误」の Issue から、リージョン、クライアントバージョン、テンプレート、完全な `code_sha256` を確認し、
   具体的に異なるフィールドを記録します。ゲームバージョン、テンプレート、検出方式の異なるコードを混ぜ、コード全体を誤りと判定してはいけません。
2. **ローカルの証拠の確認。** 対応するクライアントバージョンで、候補の検証結果、実際のマッチング通知、コンテンツへの出入り、記録タイムラインを確認します。再ログインしていない、観察不足、収集異常などの要因を除外します。
   「まだ観察されていない」と「矛盾を検出した」は異なります。提出者数、アカウントの身元、公開順、一度の使用感だけでは、この確認を代替できません。
3. **証拠に基づく処理。** コードが実際の動作と矛盾すると確認できた場合は、そのコードだけを取り消します。証拠が不足していれば候補を残し、必要な観察を説明します。
   両方とも検証に合格する場合は両方を残し、再現可能な結果を説明します。ラベルを消すためだけに唯一の正解を選ばず、`conflicting` は引き続きフィールドの差異から自動計算します。
4. **結論の公開。** 関連する Issue に、リージョン、バージョン、候補の完全な識別子、異なるフィールド、検証根拠、結論、実施した処理を記載し、提出者が確認できるようにします。
   生のメッセージ、キャラクター情報、その他の個人情報の提出は求めません。後から新しい証拠が得られた場合は説明を追記します。

### 取り消しと再確認の実行方法

**この公開リポジトリ**の最新のローカルコピーで、誤りを確認したコードに対して実行します。

```bash
python tools/publish.py revoke --repo . --code-sha256 <确认有误的校准码完整编号>
```

スクリプトが変更するのはローカルファイルです。`index.json` などの差分を確認し、このリポジトリの `main` にコミットしてプッシュした後に、オンラインのインデックスが更新されます。
`revoke` は取り消したエントリを保持し、関連フラグを再計算します。また、そのコードを提出したアカウントは、対応するリージョンとバージョンへの提出が停止します。詳しくは「取り消し」を参照してください。
`conflicting` や `submitters` だけを手で変更して、裁定結果を作らないでください。これらは、その後の公開や再計算で再生成されます。

`remark` はフラグの再計算だけを行い、正誤の裁定やコードの取り消しはしません。`lift` は指定したリージョンとバージョンでのアカウントの受け付け停止だけを解除し、取り消し済みのコードを復活させません。
訂正が必要なプレイヤーは、新しい正しいコードを改めて共有してください。クライアントが取り消しを認識するまでには、インデックスの更新間隔やダウンロードキャッシュも影響します。コマンドを実行した瞬間に、すべての PC に反映されるわけではありません。

## キャリブレーションの不具合を報告

使用中のコードに問題がある場合（マッチング通知の誤検出、記録できない、ジョブやコンテンツが誤っているなど）は、
[「报告校准有误」フォーム](../../issues/new?template=report-calibration.yml)に現象を記載してください。リージョン、クライアントバージョン、現象だけでよく、コードを添付する必要はありません。

通常の文章による報告は、自動で `evidence-waiting` に分類し、票としては数えません。システムが、ソフトウェアでプレビューした最小限の要約を使って新しい証拠 Issue を作るよう案内し、前述のルールで自動処理します。
**報告件数だけでコードを自動取り消し・隔離したり、アカウントを凍結したりすることはありません。** メンテナーがそのリージョンのゲームを所有するまで待つ必要もありません。

## テンプレートがないリージョンでの開始方法

ソフトウェアのテンプレートなし収集ガイドで、明示的に収集を開始し、ログイン、コンテンツ申請、マッチング、コンテンツへの出入りなどの操作をマークしてから停止します。プレビュー後、自分の操作で
[新リージョンの候補情報](../../issues/new?template=template-observation.yml)を提出します。要約に含むのは、操作、通信方向、opcode、長さ、観察ウィンドウ内外の件数など、固定されたメタデータだけです。
生のペイロード、ペイロードのハッシュ、接続タグ、キャラクター、IP、デバイス識別子、正確なタイムラインは含みません。
リポジトリはメタデータのハッシュで重複を排除し、`candidates/<哈希>.json` に保存します。状態は常に **CANDIDATE / BLOCKED** とし、フィールドのオフセット、ルーレットの識別、
ゾーン変更とクリアの意味、対象リージョンの実機検証など、足りない情報を列挙します。中国リージョンの定数の流用、完全なプロトコルの捏造、VERIFIED の生成、テンプレートの動的な有効化は行いません。
正式なテンプレートは、必要な証拠がそろった後も、ソフトウェアに同梱して公開します。収集やデコードが利用できない場合は実際の失敗理由を保持し、証拠が不足する間は未対応のままにします。

## 取り消し

メンテナーは `index.json` の対象エントリの `revoked` を `true` に変更するか、次を実行します。

```bash
python tools/publish.py revoke --repo . --code-sha256 <完整编号>
```

取り消してもエントリは削除しません。まだそのコードを有効化していないソフトウェアは、取り消しフラグを読み込むと使用しなくなります。使用中で、まだ完全に検証されていないソフトウェアは、インデックスの再読み込み時に取り消しを認識し、
使用を停止して、そのコードから生成した記録を要再確認とします。完全に検証済みでインデックスを再読み込みしない共有プロファイルは、ソフトウェアがローカルトラフィックとの矛盾を検出した時点で使用を停止します。
`revoke` は、そのバージョンと、同じリージョンのそれ以降のバージョンについて、`conflicting` と `shape_prior` を再計算します。取り消したコードは比較対象から外れ、この二つのフラグも付かなくなります。
ダウンロード元にはキャッシュがあります。`raw.githubusercontent.com` では数分で反映され、jsDelivr では最大約 12 時間かかります。jsDelivr のキャッシュは利用者側で削除できないため、Action は削除を試みません。

取り消されたコードを提出したアカウントは、そのリージョンとクライアントバージョンへの提出が停止します。Action は拒否時に、提出者へ Issue での事情説明を求めます。メンテナーは再確認後に次を実行します。

```bash
python tools/publish.py lift --repo . --account id:<数字编号> --region <CN 或 GLOBAL> --build <客户端版本>
```

そのアカウントは再び提出できるようになりますが、取り消し済みのコード自体は再公開しません。取り消したコードのファイル名（識別子の先頭 12 桁）は、別のコードで再使用できます。

フラグのルールを変更した後は、メンテナーが全体または指定バージョンの二つのフラグをまとめて再計算し、過去のエントリを更新できます。

```bash
python tools/publish.py remark --repo . [--region <CN 或 GLOBAL> --build <客户端版本> …]
```

バージョンを指定しない場合、インデックス内のすべてのリージョンとバージョンを再計算します。出力は 1 行の JSON で、再計算したバージョン、変更されたエントリ数、インデックスのサイズ上限によりフラグなしで書き込んだバージョンを含みます。
指定したバージョンがインデックスにない場合は、どのファイルも変更しません。

## 古いバージョンの整理

インデックスにはサイズ上限があり、提出によってエントリが削除されることはありません。メンテナーは整理するクライアントバージョンを個別に指定できます。

```bash
python tools/publish.py prune --repo . --region <CN 或 GLOBAL> --build <客户端版本> [--build <客户端版本> …]
```

`--apply` を付けない場合は、整理対象のバージョン、エントリ数、提出台帳の記録数、コードファイルを表示するだけで、ファイルは変更しません。内容を確認した後に `--apply` を付けて実行してください。
整理対象のバージョンは、エントリ、提出台帳の記録、コードファイルとともに削除します。元のファイルはコミット履歴に残ります。同じリージョンのそれ以降のバージョンの二つのフラグも再計算し、
整理したバージョンを根拠にしなくなります。
バージョン番号は提出者が入力し、当日の日付のバージョンも受け付けるため、スクリプトが日付だけで保持対象を決めることはありません。プレイヤーが使用しなくなった古いバージョンだけを整理してください。

## リポジトリの構成

| パス | 内容 |
|---|---|
| `index.json` | 公開済みコードのインデックス。ソフトウェアがダウンロード（上限 64 KB、512 エントリ）。`conflicting`、`shape_prior`、可逆的な `quarantined` / `quarantine_epoch` を含む場合あり |
| `submissions.json` | 提出台帳。どのアカウント（数値 ID）が、どのバージョンにどのコードを提出したか、検証済みの提出か（`basis`）、置き換えた旧コードを記録。ソフトウェアはダウンロードしない |
| `cn/<客户端版本>/<编号前 12 位>.mrc` | 中国リージョンのコード。追加したコミット ID を指定してソフトウェアがダウンロード |
| `global/<客户端版本>/<编号前 12 位>.mrc` | グローバルリージョンのコード |
| `templates/<模板编号>.json` | ソフトウェア同梱テンプレートのバイト単位の複製。Action が構造の再構築・検証に使用 |
| `tools/` | 検証・公開スクリプト。MentorRecorder メインリポジトリからコピーし、このリポジトリ内では手動編集しない |
| `.github/ISSUE_TEMPLATE/share-calibration.yml` | 提出フォーム |
| `.github/ISSUE_TEMPLATE/report-calibration.yml` | 不具合報告フォーム |
| `.github/workflows/publish-calibration.yml` | 自動検証、公開、返信。30 分ごとに取りこぼした提出を補処理 |
| `.github/workflows/report-calibration.yml` | 通常の報告を自動待機にし、追加証拠を案内。重複返信を永続的に防止 |
| `.github/ISSUE_TEMPLATE/evidence-calibration.yml`、`template-observation.yml` | プレビュー済みの最小限の公開要約を提出するフォーム |
| `.github/workflows/evidence-calibration.yml` | 証拠の自動受け付け、隔離・復帰、候補保存、定期的な補処理 |
| `evidence-ledger.json`、`evidence-sweep.json` | 容量制限付きの証拠リプレイ防止記録、アカウントの最新の立場、epoch の理由、補処理カーソル。クライアントはダウンロードしない |
| `schemas/`、`candidates/` | 唯一の証拠形式定義の複製と、未対応の候補ドラフト |
| `LICENSE.md`、`LICENSES/` | ライセンス |

## データとプライバシー

- `submissions.json` には、提出アカウントの GitHub 数値 ID、提出時に選択した出所（「検証済み」の場合だけ `basis` を記録）、そのアカウントが以前に置き換えたコードのチェックサムを記録します。用途は、アカウントごとの受け付けルール（同じバージョンで同時に有効なコードは一つ、提出件数と 1 日の上限、取り消し後の受け付け停止）の適用と、差異の通知時に相手の Issue を探すことに限ります。この ID と出所は、対応する Issue でも公開されています。
  このファイルはソフトウェアにダウンロードされず、`index.json` にアカウント情報は含まれません。
- Action が使用するのは GitHub の既定の `GITHUB_TOKEN` のみで、ほかの秘密鍵やシークレットは必要ありません。
- 提出前に、許可リストに限定した要約をプレビューできます。公開 Issue にはアカウントと GitHub 上の提出時刻も表示され、本文、要約ハッシュ、ランダムなセッション別名、数値アカウント台帳が履歴やミラーに残る場合があります。
  リポジトリは、キャラクター、IP、生のメッセージ、デバイス識別子、正確なゲーム内タイムラインを求めません。Issue を一つ削除すれば、すべての履歴コピーが消えると保証するものではありません。
