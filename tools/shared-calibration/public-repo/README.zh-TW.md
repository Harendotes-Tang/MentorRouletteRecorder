# MentorRecorder 共用校準

[简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md)

本儲存庫存放「導隨記錄器」（MentorRecorder）玩家分享的**共用校準碼**。

遊戲每次更新都可能重新排列封包編號（opcode）。同一區服、同一遊戲用戶端版本的編號編譯在用戶端內，對所有玩家都相同。
因此，一名玩家在軟體中校準成功後，就可以分享結果，其他玩家的軟體不必各自重新校準。

## 執行位置與部署

目前的自動受理、隔離、恢復與候選歸檔，由 **GitHub Actions 上的 Python 規則**執行，不需要大型語言模型、模型 API 金鑰，或維護者全天開機的電腦。
玩家的電腦負責本機採證與核實；玩家確認提交後，GitHub 才會收到已預覽的摘要。正式錄製與 Npcap 封包擷取仍屬於 Windows 記錄器的功能，
本儲存庫的 Python 指令碼不會將記錄器變成 macOS 遊戲擷取用戶端。

Mac mini 可以另行設定，作為本機研究或模型輔助設備，但本儲存庫**尚未接入本機或雲端大型語言模型，也未設定自架執行器**。
目前的部署不依賴 Mac mini 開機。模型無法僅憑校準碼或摘要補出未知區服的真實協定，也無法取代本機驗證。

## 舊版用戶端相容性

新儲存庫保留 `index.json` 的 `schema_version: 1`、`MRC1.` 格式、校準碼路徑與原有提交表單。
已有共用校準功能的舊版用戶端（包括已發布的 `v1.7.2`），可以繼續讀取索引、下載並核實符合自身區服、遊戲版本及隨附範本的校準碼。
不支援共用校準的更早期用戶端，不會因為儲存庫更新而取得這項能力；範本不符或遊戲版本不受支援時，仍依原規則拒絕使用。

| 能力 | 已有共用校準功能的舊版用戶端 | 支援新證據流程的用戶端 |
|---|---|---|
| 讀取舊索引欄位與 `MRC1.` 校準碼 | 維持相容 | 支援 |
| 使用原表單提交校準碼 | 維持相容 | 支援 |
| 執行儲存庫的可逆隔離與完整核實限制 | 忽略 `quarantined` / `quarantine_epoch`，沿用舊規則 | 執行新限制，保留已在本機充分核實的設定檔 |
| 預覽並提交最小證據、無範本區服採證引導 | 沒有新入口 | 需要相應用戶端與擷取服務配套更新 |
| 沒有正式範本時自動支援新區服 | 不支援 | 同樣不支援，先收集候選線索 |

**讀取相容不代表新規則會在舊版軟體生效。** 自動隔離不會偽裝成永久 `revoked`，強迫舊版軟體停用。
本次證據功能已在原始碼中實作，但尚未作為軟體安裝包發布；只更新本儲存庫或閱讀新 README，不會替已安裝的用戶端增加新入口或隔離門檻。

## 軟體如何使用本儲存庫

- **唯讀下載。** 遊戲更新後，本機沒有可用設定檔時，軟體會讀取 `index.json`，再依提交編號下載同一區服、同一遊戲用戶端版本的校準碼檔案。
  使用中的設定檔來自共用校準且尚未完整核實，或依排隊進副本推斷配對時，軟體會以相同的最短間隔（6 小時內至多一次）重新讀取索引，以得知撤銷或更準確的校準碼。
  軟體不會向這裡上傳任何東西。
- **先核實，再使用。** 下載的校準碼還不是設定檔。軟體會先在玩家的本機流量中依結構核實：至少要等登入時的切換區域封包核實通過，才會產生設定檔並開始記錄；
  開始記錄後，排隊與進入副本封包仍會持續核實。核實不通過時會繼續本機校準，已有的校準證據不會遺失。
  錯誤的校準碼在被辨識出來之前，可能使記錄缺漏或出錯；軟體判定它與本機流量矛盾後，會停用它，並將它產生的記錄標記為待複核。
- **可以關閉。** 取得共用校準是軟體預設開啟的兩類對外連線請求之一；另一類是檢查新版本，讀取主專案發布頁上的版本號檔案，與本儲存庫無關。
  兩者都可以在設定中關閉。另外還有玩家自行開啟的線上語音，預設關閉，也與本儲存庫無關。
  請求的發出時機、攜帶內容與關閉方式，均記載於軟體的隱私範圍說明。

## 校準碼包含與不包含的內容

一份校準碼是 `MRC1.` 加上一段壓縮後的正規化 JSON。

| 包含 | 不包含 |
|---|---|
| 格式版本、區服（`CN` / `GLOBAL`）、遊戲用戶端版本號 | 角色名稱、伺服器、帳號、IP 位址 |
| 依據的隨附範本編號與範本雜湊 | 時間戳記、樣本數、排過哪些隨機任務 |
| 配對方式，以及該方式所需的封包長度、位元組偏移或狀態值 | 說明文字、檔案路徑、任何封包本文 |
| 學到的幾個封包編號（配對視窗、切換區域、副本、職業） | |

校準碼編號 `code_sha256` 是正規化內容的 SHA-256，儲存庫中的檔名取其前 12 碼。

## 提交方式

在軟體中校準成功並核對校準時間軸後，點選「分享给其他玩家」；此按鈕須由相應軟體版本提供。瀏覽器會開啟本儲存庫預填好的 Issue 頁面，
「这份校准码的来源」欄位已填為「本机校准得到，并逐条核对过校准时间线」，勾選確認後提交。GitHub Action 會自動驗證並發布，
在 Issue 下回覆結果並關閉 Issue。正常情況下不需要維護者介入。

使用其他玩家分享的校準時，軟體在本機核實通過並完整記錄過一場後，會顯示「这份校准好用，告诉其他玩家」，開啟同一份表單，
來源欄位填為「其他玩家分享，已在我的软件里核实通过并正常记录」。提交同一份校準碼會計入提交人數，讓其他玩家的軟體優先使用它。

來源欄位由軟體填寫，請勿修改：改成其他內容的提交會遭拒絕。該欄位留空時（例如代他人提交，或使用尚不支援該欄位的軟體版本），會按本機校準處理。

沒有 GitHub 帳號的玩家，可以將軟體複製出的校準碼交由他人代為提交；以下規則會按代交者的帳號計算。

## 受理規則

- 提交的 GitHub 帳號須**註冊滿 30 天**。
- 校準碼中的遊戲用戶端版本號，必須符合遊戲用戶端的版本號格式，例如 `2026.09.01.0000.0000`，
  其中的日期不得晚於提交日（按 UTC 計算）的次日。
- **每個 GitHub 帳號，在每個區服與遊戲用戶端版本中，同時只能有一份使用中的校準碼。** 此規則按帳號的數字編號計算，改名不會增加份數。
  再次提交同一份不會重複計數；提交另一份則會**替換**先前那一份，詳見下一節。
- **每個帳號的提交次數有上限**：同一區服與遊戲用戶端版本，最多先後提交 3 份不同的校準碼；每天最多為 2 個區服與遊戲用戶端版本提交，
  日期按 UTC 計算（台灣時間每天 8:00 起算新的一天）。每個開啟共用校準的軟體實例都會下載索引，而索引大小有上限；這兩項限制可避免單一帳號將索引寫滿。
- 帳號提交的校準碼經維護者撤回後，該帳號在此區服與遊戲用戶端版本下的提交會**暫停受理**，直到維護者複核，詳見「撤銷」一節。
- **不設名額上限。** 不同帳號提交完全相同的校準碼時，會合併為一筆，`submitters` 記為曾提交或核實通過該碼的不同帳號數：
  本機校準得到的提交，與「其他玩家分享，已在我的软件里核实通过」的提交適用同一套規則，同樣計數。
  軟體按提交人數由多至少決定下載與核實順序；人數相同時，沒有 `conflicting` 標記的優先，再優先選擇與上一版本結構一致（`shape_prior` 為 `true`，即結構先驗）的校準碼，
  接著按發布先後排序，詳見「校準碼彼此不一致時」。每個版本最多同時核實 8 份。
- 校準碼必須能以 `templates/` 中的隨附範本依結構重建。格式錯誤、範本不符或結構不合法的提交一律拒絕，並在 Issue 中說明原因。
- 遭拒絕的 Issue 會被關閉。修正後應提交新的 Issue，編輯已關閉的 Issue 不會重新處理。

## 更正自己提交過的校準碼

發現自己提交的那份有誤，或之後校準出更好的結果時，**不必聯絡維護者**：在軟體中再點一次「分享给其他玩家」，
照常提交新的 Issue 即可。Action 會用新的一份替換你先前為該區服與版本提交的那一份，並在回覆中說明：

- 先前那份只有你一名提交者時，會被撤回（`revoked: true`，保留項目），其他玩家的軟體不再使用它。
- 先前那份還有其他帳號提交過時，會繼續保留，只是不再計入你的提交，`submitters` 相應減一。
- 已撤回的校準碼不會再次發布，因此重新提交也無法恢復發布；請提交一份新的校準碼。
- 這種替換造成的撤回不影響你繼續提交。但若你的校準碼是被**維護者**撤回，該帳號在此區服與版本下的提交會暫停受理，
  直到維護者複核後解除；若認為撤回有誤，請在 Action 拒絕受理的 Issue 下留言說明。

## 校準碼彼此不一致時

同一區服、同一遊戲用戶端版本出現多份校準碼時，Action 會在每次發布、計入與撤銷後重新比對，並在 `index.json` 的項目上寫入兩個可選標記。
舊版軟體會忽略它們，挑選順序仍然正確。

- **`conflicting`。** 兩份校準碼會按欄位比對：切換區域封包、區域封包、職業封包，以及配對封包（配對方式與對應的長度、偏移或狀態值）。
  前三個欄位無論配對方式都會比較，配對封包只在相同配對方式內比較；校準碼中沒有的欄位不參與比較。只要任一欄位與同版本、同範本的
  另一份未撤銷校準碼不同，兩份都會標為 `conflicting: true`。此標記只表示有差異，不能單憑它判定哪份有誤。提交人數相同時，玩家的軟體會優先使用配對封包結構
  與本機上一版本核實過的設定檔一致的那份；沒有此依據時，兩份都須先在玩家本機完整核實才會啟用，直到其中一份有更多玩家提交或核實通過。
- **`shape_prior`（結構先驗）。** 與同一區服、同一配對方式、上一個有校準碼的版本相比，配對封包的結構（長度、輪盤偏移或狀態值）
  相同時為 `true`；上一版本有校準碼，但結構都不同時為 `false`；沒有可供比較的上一版本時不寫入。在本版本提交過校準碼的帳號，
  其為更早版本提交的校準碼不參與此項比較，因此單一帳號無法用自己編造的版本號，為自己的校準碼製造先驗。
  此欄位只決定下載與核實順序；玩家的軟體是否啟用一份校準碼，比較的是本機在上一版本核實過的設定檔，而非這個欄位。
  它也從不作為拒絕的依據：遊戲真的改變封包結構時，結構相同的那份反而可能有誤，因此仍須通過本機核實。

出現不一致時，Action 會在新提交 Issue 的回覆中，說明與哪個 Issue 的校準碼、在哪些欄位不一致，並在對方的 Issue 下留言一次（只在新的一份碼發布時；之後有帳號計入同一份碼，不會重複留言），
也會替雙方 Issue 加上 `conflicting` 標籤，方便維護者查找。回覆只陳述不一致，不判斷哪一份正確。
確定自己這份沒錯時，不必採取任何動作；發現自己這份有誤時，在軟體中重新分享一次即可替換。

## 校準碼衝突如何仲裁

日常仲裁由**軟體本機核實 + 儲存庫固定規則**完成，維護者不必安裝其他區服的遊戲或逐筆重現。玩家先在軟體中預覽最小摘要，
主動點選提交；儲存庫會自動驗證、去重、記錄最新立場，證據不足時自動等待。沒有背景上傳或大型語言模型。

### 自動隔離與恢復

- 使用[共用校準證據表單](../../issues/new?template=evidence-calibration.yml)。只接受 `calibration-evidence-v1`，
  唯一公開格式見 `schemas/calibration-evidence-v1.schema.json`；未知或私密欄位、重複 JSON 鍵、超出限制與不合法數值均會遭拒絕。
- 身分來源是 GitHub 即時傳回的數字帳號，註冊滿 30 天才可計票。在同一區服、遊戲版本、範本、校準碼、規則版本與欄位內，
  每個帳號只保留最新、完整且有效的一票。至少兩個不同的完整健康工作階段，對同一欄位得出相同結論才計票；重複摘要、工作階段、舊 Issue 編輯與失敗重試不會增加票數。
  尚未成票的等待摘要，可以補足至兩個真實工作階段；一個 Issue 的任一欄位成票後就會凍結，後續新立場或其他欄位，請從軟體建立新的證據 Issue。
- 同一欄位有至少 **3 個帳號 × 各 2 個健康工作階段**明確矛盾，且負向帳號嚴格多於正向帳號時，會自動設定 `quarantined`，並遞增 `quarantine_epoch`。
  新版軟體仍會下載、觀察這份碼，但必須先完整核實，不能直接啟用；已在本機完整核實的設定檔，不會因遠端隔離而撤下。
- 每個隔離原因都需要**本輪隔離後新收到**、屬於目前 epoch 的同等規模正向證據，且正向帳號多於負向帳號，才會自動恢復。
  恢復後，上一輪的負向證據不能立即再次觸發隔離；重新包裝舊工作階段，也不能製造恢復證據。
- 自動隔離不設定 `revoked`，不刪除校準碼，也不凍結帳號。多個候選可以並存。永久撤回保留為下文獨立的維護操作，系統不會依一般檢舉呼叫它。

**數量與格式只是操作門檻，無法證明提交者確實玩過遊戲、提交內容真實，或帳號彼此獨立。** 軟體最終仍依賴本機完整核實。
舊版軟體會忽略隔離欄位，繼續按原有的本機規則運作；只更新本儲存庫，不會替舊版軟體增加新門檻。
所有儲存庫寫入共用發布並行鎖；推送衝突後，會從最新的 `main` 重新計算。自動回覆為每個 Issue 一則機器人留言，重試時更新，不會重複新增；
定時 sweep 使用持久化游標，分批補處理遺漏的事件。台帳有容量上限，達上限時自動等待，不會刪除防重放記錄後，將舊證據當作新證據。
目前全域最多儲存 4096 份摘要、32768 個工作階段別名、16384 個最新欄位立場，台帳不超過 8 MiB；另有最多 4096 份一般文字報告收據。
每個帳號最多 128 份摘要、1024 個工作階段別名與 64 份文字報告，超限會回傳 `ACCOUNT_CAPACITY_WAIT`，不新增記錄；不凍結帳號，也不改變既有票數。
全域容量用盡會回傳 `LEDGER_CAPACITY_WAIT`，不承諾無限歷史，或到達上限後仍能受理新提交；不會自動丟棄防重放記錄以騰出容量。

### 軟體如何處理分歧

欄位層級共識與本機先驗，需要支援這些機制的軟體版本；只更新本儲存庫，不會替舊版軟體增加能力，舊版仍按自身的核實規則處理候選。
在支援這些機制的版本中，同一區服、遊戲用戶端版本與範本的候選，會按以下規則處理：

- **按欄位計票。** 切換區域、區域、職業分別比較，配對封包只在相同配對方式內比較；未宣告的欄位不投票。
  每個欄位分別累計支援相同取值的校準碼的 `submitters`。一份碼必須在每個有分歧的欄位上都有裁決依據，不能只因單一欄位票多，就跳過其餘欄位。
- **票多只影響優先順序與核實門檻。** 票數多於其他取值，可以作為共識依據，但不代表已證明正確；票少的碼不會因此被儲存庫撤回，也不會因此被軟體永久拒絕。
  實際啟用仍須滿足所用軟體版本的其他前置條件，並通過本機流量核實。
- **平票不任意選邊。** 只有配對封包欄位平票時，才允許以這台電腦在上一版本核實過的設定檔形狀裁決；
  只有一方與本機先驗一致，其他平票方都無此依據時，才可打破平票。其他欄位平票、雙方都有此依據，或新安裝的電腦沒有歷史設定檔時，都不能靠先驗裁決。
  儲存庫中的 `shape_prior` 只參與下載與核實順序，不能取代本機證據。
- **無法裁決就完整核實。** 沒有足夠共識或本機先驗的候選，必須先在本機完成所需的排隊、配對與進入副本等核實，再啟用。
  執行中若判定有矛盾，軟體會停用該候選，並按自身規則繼續嘗試或校準；不會將不同碼的欄位拼成一份無人校準過的「共識碼」。

例如，兩份同為 MARKER_OFFSET 的碼各有一名提交者，切換區域、區域、職業一致，配對封包分別長 24 與 40 位元組：
前三個欄位沒有分歧，配對欄位是一比一。若本機上一版本核實過的形狀只支援其中一方，就可以用它打破本機的平票；
沒有這份本機依據時，兩份都須先完整核實。儲存庫不能只因 24 位元組的形狀較常見，就撤回 40 位元組的那份。

### 可選的人工核對與永久撤回

1. **找出候選。** 從帶有 `conflicting` 標籤的提交 Issue，或「报告校准有误」的 Issue 開始，核對區服、遊戲用戶端版本、範本與完整 `code_sha256`，
   記錄具體不一致的欄位。不同遊戲版本、範本或配對方式，不能混在一起按整份碼判錯。
2. **核對本機證據。** 在對應遊戲用戶端版本中，檢查軟體的候選核實結果、實際配對視窗、進出副本與記錄時間軸；排除未重新登入、缺少觀察或擷取異常等因素。
   「尚未觀察到」不等於「已判定有矛盾」。提交人數、帳號身分、發布先後與一次使用感受，都不能單獨取代這一步。
3. **依證據處理。** 確認某份碼與真實行為矛盾時，只撤回該份碼；證據不足時保留候選，並說明還缺哪些觀察。
   若兩份都通過核實，就保留兩份並說明可重現的結果，不為了消除標籤而強行選出唯一勝者；`conflicting` 仍按欄位差異自動計算。
4. **公開說明結論。** 在相關 Issue 中記下區服、版本、候選完整編號、不一致欄位、核實依據、結論與處理動作，方便提交者複核。
   不要求提交原始封包、角色資料或其他個人資訊；之後若有新證據，應追加說明。

### 如何執行撤回與複核

在**本公開儲存庫**的最新本機副本內，對已確認有誤的碼執行：

```bash
python tools/publish.py revoke --repo . --code-sha256 <確認有誤的校準碼完整編號>
```

指令碼修改的是本機檔案；檢查 `index.json` 等檔案的差異，提交並推送至本儲存庫的 `main` 後，線上索引才會更新。
`revoke` 會保留已撤回項目、重新計算相關標記，並使提交過該碼的帳號在對應區服與版本下暫停受理；具體影響見「撤銷」。
請勿只手動修改 `conflicting` 或 `submitters` 來製造仲裁結果，這些欄位會在後續發布與重新計算時再次產生。

`remark` 只重新計算標記，不裁決對錯，也不撤回校準碼；`lift` 只解除帳號在指定區服與版本下的暫停受理，不恢復已撤回的碼。
需要更正的玩家應重新分享新的正確校準碼。用戶端得知撤回的時間，仍受索引更新間隔與下載快取影響，不會因維護者執行指令，就立即在所有電腦上生效。

## 回報校準有誤

使用的校準碼有問題（跳出視窗時誤報配對、無法記錄、職業或副本不正確等）時，可使用
[「报告校准有误」](../../issues/new?template=report-calibration.yml) 表單記錄現象：填寫區服、遊戲用戶端版本與現象即可，
不必附上校準碼。

一般文字會自動歸類為 `evidence-waiting`，不計票；系統會引導玩家使用軟體中預覽的最小摘要，建立新的證據 Issue，按上述規則自動處理。
**回報數量不會自動撤回或隔離任何校準碼，也不會凍結帳號。** 不必等待維護者擁有該區服遊戲。

## 沒有範本的區服如何開始

在軟體的無範本採證引導中明確開始、標記登入／排隊／配對／進出副本等動作並停止，預覽後主動提交
[新區服候選線索](../../issues/new?template=template-observation.yml)。摘要只包含動作與方向、opcode、長度、視窗內外計數等固定中繼資料；
不包含原始負載、負載雜湊、連線標籤、角色、IP、裝置識別碼或精確時間軸。
儲存庫依中繼資料雜湊去重，歸檔至 `candidates/<哈希>.json`，狀態始終為 **CANDIDATE / BLOCKED**，並列出欄位偏移、輪盤識別、
切換區域與通關語意、對應區服實機驗證等缺口。不會套用國服常數、編造完整協定、產生 VERIFIED，或動態啟用範本。
正式範本的證據齊全後，仍須隨軟體發布；擷取或解碼不可用時，會保留真實失敗原因，證據不足時維持不支援。

## 撤銷

維護者將 `index.json` 中對應項目的 `revoked` 改為 `true`，或執行：

```bash
python tools/publish.py revoke --repo . --code-sha256 <完整編號>
```

撤銷不會刪除項目。尚未啟用該校準碼的軟體，讀到撤銷標記後不再使用它；正在使用它、尚未完整核實的軟體，在重新讀取索引時得知撤銷後，
會停用它，並將它產生的記錄標記為待複核。已完整核實、不再讀取索引的共用設定檔，則由軟體在本機流量中判定矛盾後停用。
`revoke` 會重新計算該版本，以及同一區服更晚版本的 `conflicting` 與 `shape_prior`：已撤銷的校準碼不再參與比對，也不再帶有這兩個標記。
下載來源有快取：`raw.githubusercontent.com` 數分鐘內可見，jsDelivr 最多約 12 小時。jsDelivr 的快取無法自行清除，因此 Action 不會嘗試清除。

提交過已撤銷校準碼的帳號，在該區服與遊戲用戶端版本下暫停受理；Action 拒絕時會請提交者在 Issue 下說明情況。維護者複核後執行：

```bash
python tools/publish.py lift --repo . --account id:<數字編號> --region <CN 或 GLOBAL> --build <遊戲用戶端版本>
```

該帳號隨即可以重新提交，但已撤銷的校準碼本身仍不會再次發布。已撤銷校準碼占用的檔名（編號前 12 碼），可以由另一份校準碼重新使用。

標記規則改變後，維護者可以一次重新計算全部或指定版本的兩個標記，用來補齊先前寫出的項目：

```bash
python tools/publish.py remark --repo . [--region <CN 或 GLOBAL> --build <遊戲用戶端版本> …]
```

未指定版本時，會重新計算索引中的全部區服與版本。輸出一行 JSON，列出重新計算的版本、變更項目數，以及因索引大小上限而寫成不帶標記的版本。
指定版本不在索引中時，不會修改任何檔案。

## 清理舊版本

索引有大小上限，項目不會因為提交而刪除。維護者可以逐一指定要清理的遊戲用戶端版本：

```bash
python tools/publish.py prune --repo . --region <CN 或 GLOBAL> --build <遊戲用戶端版本> [--build <遊戲用戶端版本> …]
```

未加 `--apply` 時，只列出即將清理的版本、項目數、提交台帳記錄數與校準碼檔案，不會修改任何檔案；核對無誤後，加上 `--apply` 執行。
清理時會一併移除該版本、對應項目、提交台帳記錄與校準碼檔案，原檔仍保留在提交歷史中；同一區服更晚版本的兩個標記會隨之重新計算，
不再以清理掉的版本為依據。
指令碼不會依日期自行決定保留哪些版本，因為版本號由提交者提供，日期為當天的版本也會受理。只應清理已無玩家使用的舊版本。

|---|---|

| `submissions.json` | 提交台帳：哪個帳號（數字編號）為哪個版本提交哪份校準碼、是否在核實通過後提交（`basis`），以及它替換的舊碼；軟體不會下載此檔 |
| `cn/<客户端版本>/<编号前 12 位>.mrc` | 國服校準碼文字，軟體按加入它的提交編號下載 |
| `global/<客户端版本>/<编号前 12 位>.mrc` | 國際服校準碼文字 |
| `templates/<模板编号>.json` | 軟體隨附範本的逐位元組副本，Action 用於依結構重建驗證 |
| `tools/` | 驗證與發布指令碼，由 MentorRecorder 主儲存庫複製，不在本儲存庫內手動修改 |
| `.github/ISSUE_TEMPLATE/share-calibration.yml` | 提交表單 |
| `.github/ISSUE_TEMPLATE/report-calibration.yml` | 回報校準有誤的表單 |
| `.github/workflows/publish-calibration.yml` | 自動驗證、發布、回覆；每 30 分鐘補處理一次遺漏的提交 |
| `.github/workflows/report-calibration.yml` | 一般回報自動等待、引導補證據與持久化防止重複回覆 |
| `.github/ISSUE_TEMPLATE/evidence-calibration.yml`、`template-observation.yml` | 預覽後的最小公開摘要表單 |
| `.github/workflows/evidence-calibration.yml` | 自動證據受理、隔離恢復、候選歸檔與定時補處理 |
| `evidence-ledger.json`、`evidence-sweep.json` | 有界的證據防重放、最新帳號立場、epoch 原因與補處理游標；用戶端不會下載 |
| `schemas/`、`candidates/` | 唯一證據格式副本與尚未支援的候選草案 |
| `LICENSE.md`、`LICENSES/` | 授權 |

## 資料與隱私

- `submissions.json` 記錄提交帳號的 GitHub 數字編號、提交時選擇的來源（只有在「核实通过」時才記錄 `basis`），以及該帳號先前被替換掉的校準碼檢查值；僅用於執行受理規則中按帳號計算的各項限制（每個帳號每個版本同時只保留一份有效校準碼、提交份數與每日次數上限、撤銷後暫停受理），以及在說明不一致時找到對方的 Issue；該編號與來源原本就公開於對應的 Issue。
  軟體不會下載此檔，`index.json` 中不包含任何帳號資訊。
- Action 只使用 GitHub 提供的預設 `GITHUB_TOKEN`，不需要其他金鑰。
- 提交前會預覽白名單摘要；公開 Issue 也會公開帳號與 GitHub 的提交時間，其本文、摘要雜湊、隨機工作階段別名與數字帳號台帳，可能保留在歷史與鏡像中。
  儲存庫不索取角色、IP、原始封包、裝置識別碼或精確遊戲時間軸，也不承諾刪除一個 Issue 就能刪除所有歷史副本。
