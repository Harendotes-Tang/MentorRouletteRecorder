# MentorRecorder 共享校准

[简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md)

本仓库存放「导随记录器」（MentorRecorder）玩家分享的**共享校准码**。

游戏每次更新都可能重排报文编号（opcode）。同一区服、同一客户端版本的编号编译在客户端内，对所有玩家一致。
因此一名玩家在软件中校准成功后，可以将结果分享出来，其他玩家的软件无需逐一重新校准。

## 执行位置与部署

当前自动受理、隔离、恢复和候选归档由 **GitHub Actions 上的 Python 规则**执行，不需要大模型、模型 API 密钥或维护者的常开电脑。
玩家电脑负责本机采证和核实；玩家确认提交后，GitHub 才会收到预览过的摘要。正式录制与 Npcap 抓包仍属于 Windows 记录器，
本仓库的 Python 脚本不会把记录器变成 macOS 游戏采集客户端。

Mac mini 可以作为另行配置的本地研究或模型辅助设备，但本仓库**尚未接入本地或云端大模型，也未配置自托管运行器**。
当前部署不依赖 Mac mini 开机。模型不能凭校准码或摘要补出未知区服的真实协议，也不能替代本机验证。

## 旧客户端兼容性

新仓库保留 `index.json` 的 `schema_version: 1`、`MRC1.` 格式、校准码路径和原提交表单。
已有共享校准功能的旧客户端（包括已发布的 `v1.7.2`）可以继续读取索引、下载和核实匹配自身区服、游戏版本与随包模板的校准码。
不支持共享校准的更早客户端不会因仓库更新而获得这项能力；模板不匹配或游戏版本不受支持时，仍按原规则拒绝使用。

| 能力 | 已有共享校准功能的旧客户端 | 支持新证据流程的客户端 |
|---|---|---|
| 读取旧索引字段与 `MRC1.` 校准码 | 保持兼容 | 支持 |
| 使用原表单提交校准码 | 保持兼容 | 支持 |
| 执行仓库的可逆隔离与完整核实限制 | 忽略 `quarantined` / `quarantine_epoch`，沿用旧规则 | 执行新限制，保留已在本机充分核实的档案 |
| 预览并提交最小证据、无模板区服采证引导 | 没有新入口 | 需要相应客户端与采集服务配套更新 |
| 无正式模板时自动支持新区服 | 不支持 | 同样不支持，先收集候选线索 |

**兼容读取不等于新规则对旧软件生效。** 自动隔离不会伪装成永久 `revoked` 来强迫旧软件停用。
本次证据功能已在源码中实现，但尚未作为软件安装包发布；仅更新本仓库或阅读新 README，不会给已安装客户端增加新入口或隔离门槛。

## 软件如何使用本仓库

- **只读下载。** 游戏更新后本机没有可用档案时，软件读取 `index.json`，再按提交号下载同一区服、同一客户端版本的校准码文件。
  在用的档案来自共享校准而尚未完整核实，或者按排本推断匹配时，软件以相同的最短间隔（6 小时内至多一次）重新读取索引，以便得知撤销或更准的校准码。
  软件不向这里上传任何东西。
- **先核实，再使用。** 下载的校准码不是档案。软件先在玩家本机流量中按结构核实：至少要等登录时的换区报文核实通过，才生成档案并开始记录；
  开始记录后，排本与进本报文仍会继续核实。核实不通过时继续本机校准，已有的校准证据不会丢失。
  一份错误的校准码在被识别出来之前，可能使记录缺失或有误；软件判出它与本机流量矛盾后会停用它，并把它生成的记录标记为待复核。
- **可以关闭。** 获取共享校准是软件默认开启的两类出站请求之一；另一类是检查新版本，读取主项目发布页上的版本号文件，与本仓库无关。
  两者都可以在设置中关闭。此外还有玩家自行开启的在线语音，默认关闭，同样与本仓库无关。
  请求的发出时机、携带内容与关闭方式，均写在软件的隐私边界说明中。

## 校准码包含与不包含的内容

一份校准码是 `MRC1.` 加上一段压缩后的规范化 JSON。

| 有 | 没有 |
|---|---|
| 格式版本、区服（`CN` / `GLOBAL`）、客户端版本号 | 角色名、服务器、账号、IP 地址 |
| 依据的随包模板编号与模板哈希 | 时间戳、样本数、排过哪些随机任务 |
| 匹配方式，以及这种方式需要的报文长度、字节偏移或状态值 | 说明文字、文件路径、任何报文正文 |
| 学到的几个报文编号（匹配弹窗、换区、副本、职业） | |

校准码的编号 `code_sha256` 是规范化内容的 SHA-256，仓库中的文件名取其前 12 位。

## 提交方式

在软件中校准成功并核对校准时间线之后，点击「分享给其他玩家」，该按钮需要由相应的软件版本提供。浏览器会打开本仓库预填好的 Issue 页面，
「这份校准码的来源」一栏已填为「本机校准得到，并逐条核对过校准时间线」，勾选确认后提交。GitHub Action 会自动校验并发布，
在 Issue 下回复结果并关闭 Issue。正常情况下无需维护者参与。

使用其他玩家分享的校准时，软件在本机核实通过并完整记录过一场之后，会给出「这份校准好用，告诉其他玩家」，打开同一个表单，
来源一栏填为「其他玩家分享，已在我的软件里核实通过并正常记录」。提交同一份校准码会计入提交人数，让其他玩家的软件更优先使用它。

来源一栏由软件填写，请不要改动：改成其他内容的提交会被拒绝。该栏留空（例如代人提交，或使用尚不支持该栏的软件版本）时按本机校准处理。

没有 GitHub 账号的玩家可以将软件复制出的校准码交由他人代为提交，下述规则按代交者的账号计算。

## 受理规则

- 提交的 GitHub 账号**注册满 30 天**。
- 校准码里的客户端版本号必须是游戏客户端的版本号格式，形如 `2026.09.01.0000.0000`，
  其中的日期不得晚于提交日（按 UTC 计算）的次日。
- **每个 GitHub 账号，每个区服与客户端版本，同时只有一份在用的校准码。** 该规则按账号的数字编号计算，改名不能增加份数。
  再次提交同一份不重复计数；提交另一份则**替换**先前那一份，见下一节。
- **每个账号的提交次数有上限**：同一区服与客户端版本最多先后提交 3 份不同的校准码；每天最多为 2 个区服与客户端版本提交，
  日期按 UTC 计算（北京时间每天 8:00 起算新的一天）。每个开启了共享校准的软件实例都会下载索引，而索引大小有上限，这两条限制使单个账号无法把它写满。
- 账号提交的校准码被维护者撤回之后，该账号在这个区服与客户端版本下的提交**暂停受理**，直到维护者复核，见「撤销」一节。
- **不设名额上限。** 不同账号提交完全相同的校准码时合并为一条，`submitters` 记为提交或核实通过过它的不同账号数：
  本机校准得到的提交与「其他玩家分享，已在我的软件里核实通过」的提交适用同一套规则，同样计数。
  软件按提交人数从多到少决定下载与核实的先后；人数相同时，没有 `conflicting` 标记的在前，再优先与上一版本结构一致（`shape_prior` 为 `true`，即结构先验）的，
  再按发布先后，见「校准码之间不一致时」。每个版本最多同时核实 8 份。
- 校准码必须能用 `templates/` 中的随包模板按结构重建。格式错误、模板不匹配或结构不合法的提交一律拒绝，并在 Issue 中说明原因。
- 被拒绝的 Issue 将被关闭。修正后应提交新的 Issue，编辑已关闭的 Issue 不会被重新处理。

## 更正自己提交过的校准码

发现自己提交的那一份有误，或后来校准出了更好的一份时，**不需要联系维护者**：在软件里重新点一次「分享给其他玩家」，
照常提交新的 Issue 即可。Action 会用新的一份替换你先前为该区服与版本提交的那一份，并在回复中说明：

- 先前那一份只有你一个提交者时，它会被撤回（`revoked: true`，条目保留），其他玩家的软件不再使用它。
- 先前那一份还有别的账号也提交过时，它继续保留，只是不再计入你的提交，`submitters` 相应减一。
- 已被撤回的校准码不会再次发布，因此重新提交也无法恢复发布；请提交一份新的。
- 这样替换下来的校准码不影响你继续提交。但如果你的校准码是被**维护者**撤回的，这个账号在该区服与版本下的提交会暂停受理，
  直到维护者复核后解除；如认为撤回有误，请在 Action 拒绝受理的那个 Issue 下留言说明情况。

## 校准码之间不一致时

同一区服、同一客户端版本出现多份校准码时，Action 在每次发布、计入与撤销后重新比对，并在 `index.json` 的条目上写两个可选标记。
旧版软件忽略它们，挑选顺序仍然正确。

- **`conflicting`。** 两份校准码按字段比对：换区报文、区域报文、职业报文，以及匹配报文（匹配方式与相应的长度、偏移或状态值）。
  前三个字段不论匹配方式都比较，匹配报文只在同一匹配方式内比较；校准码里没有的字段不参与比较。只要在任一字段上与同版本、同模板的
  另一份未撤销校准码不同，两份都会标为 `conflicting: true`。这个标记只说明存在差异，不能单凭它断定哪份有误。提交人数相同时，玩家的软件优先使用匹配报文结构
  与它自己在上一版本核实过的档案一致的那一份；没有这样的依据时，两份都要先在玩家本机完整核实才会启用，直到其中一份被更多玩家提交或核实通过。
- **`shape_prior`（结构先验）。** 与同一区服、同一匹配方式的上一个有校准码的版本相比，匹配报文的结构（长度、轮盘偏移或状态值）
  相同时为 `true`，上一版本有校准码但结构都不同时为 `false`，没有可比的上一版本时不写。在本版本提交过校准码的账号，
  它们为更早版本提交的校准码不参与这项比较，一个账号因此无法用自己编造的版本号为自己的校准码制造先验。
  它只决定下载与核实的先后，玩家的软件是否启用一份校准码，比较的是本机自己在上一版本核实过的档案，而不是这个字段；
  它也从不作为拒绝的依据：游戏真的改了报文结构时，结构相同的那份反而可能是错的，所以它仍要通过本机核实。

出现不一致时，Action 在新提交的 Issue 的回复里说明与哪个 Issue 的校准码在哪些字段上不一致，在对方的 Issue 下评论一次（只在新的一份码发布时；再有账号计入同一份码不重复评论），
并给双方的 Issue 打上 `conflicting` 标签，维护者按标签即可找到。回复只陈述不一致，不判断哪一份正确。
确定自己这份没错时不需要做什么；发现是自己这份有误时，在软件里重新分享一次即可替换。

## 校准码冲突如何仲裁

日常仲裁由**软件本机核实 + 仓库固定规则**完成，维护者无需安装其他区服游戏或逐条复现。玩家先在软件中预览最小摘要，
主动点击提交；仓库自动校验、去重、记录最新立场，证据不足自动等待。没有后台上传或大模型。

### 自动隔离与恢复

- 使用[共享校准证据表单](../../issues/new?template=evidence-calibration.yml)。只接受 `calibration-evidence-v1`，
  唯一公开格式见 `schemas/calibration-evidence-v1.schema.json`；未知或私密字段、重复 JSON 键、超限和不合法数值均拒绝。
- GitHub 实时返回的数字账号是身份来源，注册满 30 天才可计票。同一区服、游戏版本、模板、校准码、规则版本与字段内，
  每个账号只保留最新完整有效的一票。至少两个不同的完整健康会话，对同一字段同一结论才计票；重复摘要、会话、旧 Issue 编辑和失败重试不加票。
  未成票的等待摘要允许补到两个真实会话；一个 Issue 任一字段成票后便冻结，后续新立场或其他字段请从软件新建证据 Issue。
- 同一字段有至少 **3 个账号 × 各 2 个健康会话**明确矛盾，且负向账号严格多于正向时，自动设置 `quarantined`，递增 `quarantine_epoch`。
  新版软件仍下载、观察这份码，但须先完整核实，不能直接启用；已经本机完整核实的档案不因远端隔离撤下。
- 每个隔离原因都需要**本轮隔离后新接收**、属于当前 epoch 的同规模正向证据，并且正向账号多于负向，才能自动恢复。
  恢复后旧一轮负向证据不能立即再次触发隔离；重新包装旧会话也不能制造恢复证据。
- 自动隔离不设置 `revoked`，不删码、不冻结账号。多个候选可以共存。永久撤回保留为下文独立的维护操作，系统不会按普通举报调用它。

**数量与格式只是操作门槛，无法证明提交者确实玩过游戏、提交内容真实或账号相互独立。** 软件最终仍依赖本机完整核实。
旧版软件会忽略隔离字段，仍按原有本机规则运行；仅更新本仓库不会为旧软件增加新门槛。
所有仓库写入共用发布并发锁；推送冲突后从最新 `main` 重算。自动回复为每 Issue 一条机器人评论，重试更新而不叠加；
定时 sweep 用持久游标分批补处理遗漏的事件。台账有容量上限，达到上限自动等待，不删除防重放记录后假装新证据。
当前全局最多保存 4096 份摘要、32768 个会话别名、16384 个最新字段立场，台账不超过 8 MiB；另有最多 4096 份普通文字报告收据。
每账号最多 128 份摘要、1024 个会话别名和 64 份文字报告，超限返回 `ACCOUNT_CAPACITY_WAIT` 而不占新记录；不冻结账号或改变已有票。
全局容量耗尽返回 `LEDGER_CAPACITY_WAIT`，不承诺无限历史或到达上限后仍能新增受理；不会自动丢弃防重放记录来腾容量。

### 软件如何处理分歧

字段级共识与本机先验需要支持这些机制的软件版本；只更新本仓库不会给旧版软件增加能力，旧版仍按自身的核实规则处理候选。
在支持这些机制的版本中，同一区服、客户端版本与模板的候选按以下规则处理：

- **按字段计票。** 换区、区域、职业分别比较，匹配报文只在同一匹配方式内比较；未声明的字段不投票。
  每个字段分别累计支持相同取值的校准码的 `submitters`。某份码必须在每个有分歧的字段上都有裁决依据，不能只因一个字段票多就跳过其余字段。
- **票多仅影响优先级和核实门槛。** 票数多于其他取值可作为共识依据，不代表已证明正确；票少的码不会因此被仓库撤回，也不会因此被软件永久拒绝。
  实际启用仍需满足所用软件版本的其他前置条件，并通过本机流量核实。
- **平票不随意选边。** 只有匹配报文字段的平票，才允许用这台机器在上一版本核实过的档案形状裁决；
  只有一方与本机先验一致、其他平票方均无该依据时才可打破平票。其他字段平票、双方都有该依据，或新装机器没有历史档案时，都不能靠先验裁决。
  仓库里的 `shape_prior` 只参与下载和核实顺序，不能代替本机证据。
- **无法裁决就完整核实。** 没有足够共识或本机先验的候选，须先在本机完成所需的排本、匹配与进本等核实，再启用。
  运行中若判出矛盾，软件停用该候选并按自身规则继续尝试或校准；不会把不同码的字段拼成一份无人校准过的“共识码”。

例如，两份同为 MARKER_OFFSET 的码各有一名提交者，换区、区域、职业一致，匹配报文分别长 24 和 40 字节：
前三个字段没有分歧，匹配字段为一比一。若本机上一版本核实过的形状只支持其中一方，可以用它打破本机的平票；
没有这份本机依据时，两份都先完整核实。仓库不能仅因 24 字节的形状更常见，就撤回 40 字节那份。

### 可选的人工核对与永久撤回

1. **定位候选。** 从带 `conflicting` 标签的提交 Issue，或「报告校准有误」的 Issue 开始，核对区服、客户端版本、模板与完整 `code_sha256`，
   记录具体不一致的字段。不同游戏版本、模板或匹配方式不能混在一起按整码判错。
2. **核对本机证据。** 在对应客户端版本中检查软件的候选核实结果、实际匹配弹窗、进出本及记录时间线；排除未重新登录、缺少观察或采集异常等因素。
   “尚未观察到”不等于“已判出矛盾”。提交人数、账号身份、发布早晚和一次使用感受，都不能单独替代这一步。
3. **按证据处理。** 确认某份码与真实行为矛盾时，只撤回这份码；证据不足时保留候选，说明还缺什么观察。
   如果两份都通过核实，就保留两份并说明可复现的结果，不为了消除标签而强行选出唯一赢家；`conflicting` 仍按字段差异自动计算。
4. **公开说明结论。** 在相关 Issue 中记下区服、版本、候选完整编号、不一致字段、核实依据、结论及处理动作，便于提交者复核。
   不要求提交原始报文、角色资料或其他个人信息；若后来有新证据，应追加说明。

### 如何执行撤回与复核

在**本公开仓库**的最新本地副本内，对已经确认有误的码执行：

```bash
python tools/publish.py revoke --repo . --code-sha256 <确认有误的校准码完整编号>
```

脚本修改的是本地文件；检查 `index.json` 等文件的差异，提交并推送到本仓库 `main` 后，线上索引才会更新。
`revoke` 会保留被撤回条目、重算相关标记，并使提交过该码的账号在对应区服与版本下暂停受理；具体影响见「撤销」。
不要只手改 `conflicting` 或 `submitters` 来制造仲裁结果，它们会在后续发布与重算时重新生成。

`remark` 只重算标记，不裁决对错，也不撤回校准码；`lift` 只解除账号在指定区服与版本下的暂停受理，不恢复已经撤回的码。
需要更正的玩家应重新分享新的正确校准码。客户端获知撤回还受索引刷新间隔和下载缓存影响，不会因维护者执行命令就立即在所有机器上生效。

## 报告校准有误

用到的校准码有问题（弹窗时误报匹配、记录不到、职业或副本不对等）时，用
[「报告校准有误」](../../issues/new?template=report-calibration.yml) 表单记录现象：填区服、客户端版本与现象即可，
不必附上校准码。

普通文字自动归为 `evidence-waiting`，不计票；系统会指引玩家使用软件预览的最小摘要新建证据 Issue，按上述规则自动处理。
**报告数量不会自动撤回或隔离任何校准码，也不会冻结账号。** 无需等待维护者拥有该区服游戏。

## 没有模板的区服如何开始

在软件的无模板采证引导中明确开始、标记登录/排本/匹配/进出本等动作并停止，预览后主动提交
[新区服候选线索](../../issues/new?template=template-observation.yml)。摘要只含动作与方向、opcode、长度、窗口内外计数等固定元数据；
不含原始负载、负载哈希、连接标签、角色、IP、设备标识或精确时间线。
仓库按元数据哈希去重归档 `candidates/<哈希>.json`，始终为 **CANDIDATE / BLOCKED**，列出字段偏移、轮盘身份、
换区与通关语义、对应区服实机验证等缺口。不会套用国服常量、编造完整协议、生成 VERIFIED 或动态启用模板。
正式模板证据齐全后仍随软件发布；采集或解码不可用时保留真实失败原因，证据不足保持不支持。

## 撤销

维护者将 `index.json` 中对应条目的 `revoked` 改为 `true`，或执行：

```bash
python tools/publish.py revoke --repo . --code-sha256 <完整编号>
```

撤销不会删除条目。尚未启用该校准码的软件读到撤销标记后不再使用它；正在使用它、尚未完整核实的软件在重新读取索引时得知撤销，
停用它，并把它生成的记录标记为待复核。已完整核实、不再读取索引的共享档案，由软件在本机流量中判出矛盾后停用。
`revoke` 会重算该版本以及同一区服更晚版本的 `conflicting` 与 `shape_prior`：被撤销的校准码不再参与比对，也不再带这两个标记。
下载源存在缓存：`raw.githubusercontent.com` 数分钟内可见，jsDelivr 最多约 12 小时。jsDelivr 的缓存无法自助清除，因此 Action 不会尝试清除。

提交过被撤销校准码的账号，在该区服与客户端版本下暂停受理；Action 拒绝时会请提交者在 Issue 下说明情况。维护者复核后执行：

```bash
python tools/publish.py lift --repo . --account id:<数字编号> --region <CN 或 GLOBAL> --build <客户端版本>
```

该账号随即可以重新提交，被撤销的校准码本身仍不会再次发布。被撤销的校准码所占用的文件名（编号前 12 位）可以由另一份校准码重新使用。

标记的规则改变之后，维护者可以一次性重算全部或指定版本的两个标记，用于补齐此前写出的条目：

```bash
python tools/publish.py remark --repo . [--region <CN 或 GLOBAL> --build <客户端版本> …]
```

不指定版本时重算索引中的全部区服与版本。输出一行 JSON，列出重算的版本、发生变化的条目数，以及因索引大小上限而写成不带标记的版本。
指定的版本不在索引中时不改动任何文件。

## 清理旧版本

索引有大小上限，条目不会因提交而删除。维护者可以逐个指定要清理的客户端版本：

```bash
python tools/publish.py prune --repo . --region <CN 或 GLOBAL> --build <客户端版本> [--build <客户端版本> …]
```

不加 `--apply` 时只列出将被清理的版本、条目数、提交台账记录数与校准码文件，不改动任何文件；核对无误后加 `--apply` 执行。
被清理的版本连同其条目、提交台账记录与校准码文件一并移除，原文件仍保留在提交历史中；同一区服更晚版本的两个标记随之重算，
不再以被清理的版本为依据。
脚本不按日期自行决定保留哪些版本，因为版本号由提交者给出，日期为当天的版本也会被受理。只应清理已无玩家使用的旧版本。

## 仓库布局

| 路径 | 内容 |
|---|---|
| `index.json` | 已发布校准码的索引，软件下载它（上限 64 KB、512 条）；可带 `conflicting`、`shape_prior` 和可逆 `quarantined` / `quarantine_epoch` |
| `submissions.json` | 提交台账：哪个账号（数字编号）为哪个版本提交了哪份校准码、是否为核实通过后提交（`basis`），以及它替换掉的旧码；软件不下载该文件 |
| `cn/<客户端版本>/<编号前 12 位>.mrc` | 国服校准码文本，软件按添加它的提交号下载 |
| `global/<客户端版本>/<编号前 12 位>.mrc` | 国际服校准码文本 |
| `templates/<模板编号>.json` | 软件随包模板的逐字节副本，Action 用来按结构重建校验 |
| `tools/` | 校验与发布脚本，从 MentorRecorder 主仓库复制，不在本仓库内手工修改 |
| `.github/ISSUE_TEMPLATE/share-calibration.yml` | 提交表单 |
| `.github/ISSUE_TEMPLATE/report-calibration.yml` | 报告校准有误的表单 |
| `.github/workflows/publish-calibration.yml` | 自动校验、发布、回复；每 30 分钟补处理一次遗漏的提交 |
| `.github/workflows/report-calibration.yml` | 普通报告自动等待、指引补证据与持久化防重复回复 |
| `.github/ISSUE_TEMPLATE/evidence-calibration.yml`、`template-observation.yml` | 预览后的最小公开摘要表单 |
| `.github/workflows/evidence-calibration.yml` | 自动证据受理、隔离恢复、候选归档与定时补处理 |
| `evidence-ledger.json`、`evidence-sweep.json` | 有界证据防重放、最新账号立场、epoch 原因与补处理游标；客户端不下载 |
| `schemas/`、`candidates/` | 唯一证据格式副本与未获支持的候选草案 |
| `LICENSE.md`、`LICENSES/` | 许可 |

## 数据与隐私

- `submissions.json` 记录提交账号的 GitHub 数字编号、提交时选择的来源（仅在「核实通过」时记 `basis`），以及该账号此前被替换掉的校准码的校验值，仅用于执行受理规则中按账号计算的各项限制（每个账号每个版本同时只保留一份有效校准码、提交份数与每日次数上限、撤销后暂停受理）与说明不一致时找到对方的 Issue；该编号与来源在对应的 Issue 上本就是公开的。
  该文件不会被软件下载，`index.json` 中不含任何账号信息。
- Action 只使用 GitHub 提供的默认 `GITHUB_TOKEN`，不需要任何其他密钥。
- 提交前预览白名单摘要；公开 Issue 同时公开账号与 GitHub 的提交时间，其正文、摘要哈希、随机会话别名和数字账号台账可能保留在历史和镜像中。
  仓库不索取角色、IP、原始报文、设备标识或精确游戏时间线，不承诺删除一个 Issue 就能删除所有历史副本。
