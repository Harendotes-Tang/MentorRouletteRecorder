# Community reminders and macros

MentorRecorder can read this directory without signing in to GitHub. Use **Public library → Refresh** to see available entries. Import a reminder or macro to use it offline, and compare revisions before applying updates.

## Contribute

1. In MentorRecorder, select reminders and macros and review the public preview.
2. Select CC BY 4.0 or CC BY-SA 4.0. Only share work you may license under that choice, and keep author and source attribution for adaptations. Existing calibration data uses its own license.
3. Submit with your GitHub account from the app, or copy the complete structured block into the **Share a mentor reminder or macro** Issue form. The Issue and content are public.
4. Check the Issue for its processing result. Community submissions have not been verified for gameplay accuracy. A maintainer can independently review an item through the community workflow.

The same text is published once. An item whose body matches a live item of the same type (after unifying line breaks and dropping spaces at line ends and blank lines at either end) is left out, the rest of the submission is published, and the receipt names the published item to import instead; links to a left-out new item point at the published one. An author's edit whose new text repeats another item keeps the published version. A submission that publishes nothing new and keeps nothing unchanged is labelled `community-duplicate`. Text that reads almost the same (a Dice coefficient of at least 0.9 over neighbouring characters, after NFKC normalization, dropping sound cues and spacing, and lower-casing) is published, listed in the receipt and labelled `community-similar` with the first receipt; a maintainer may remove that label once reviewed.

The stable ID stays unchanged when the author edits a title. For an update from a new Issue, refresh the public library before previewing the submission. For an adaptation, start from a separate ID and keep the original source and license. Closing an unprocessed Issue prevents its publication. To withdraw items you published, choose **从共享库撤回** (withdraw from the public library) in MentorRecorder and paste the block it copies into the same Issue form, from the GitHub account that published them. The block names 1 to 20 IDs (`{"schema_version":1,"withdraw":[…]}`); if any of them is not in the library or was published by another account, nothing changes. Withdrawn items get the `withdrawn` status and a new revision, their text and links stay, MentorRecorder no longer lists them, installed copies show them as withdrawn and nobody can import them any more. The Issue is labelled `community-withdrawn`. A withdrawal does not count toward the daily limit below and cannot be undone by its author: a withdrawn ID is never published again, so share the text again as a new item. Withdrawn items stay in the snapshot for 30 days so that installed copies can show the withdrawal; the scheduled workflow run then deletes them the way the maintainer's `removed` status does, and their IDs are recorded so they are never published again. For a status correction, ask a maintainer. Imported notes remain with their users.

Every live entry gets one comment from the workflow in its Issue, starting with `<!-- mr-community-like:<ID> -->`. A 👍 reaction on that comment is a like for that entry, so an Issue that published several entries counts them apart. The scheduled run posts the missing comments (at most 20 a run), reads the 👍 on every like comment and writes `community/v1/likes.json` (`{"schema_version":1,"likes":{ID:{"count","issue","comment"}}}`, live entries only). The file is not part of the snapshot or its hash, so new likes never start a new generation. MentorRecorder reads it with each refresh of its shared library and opens the like comment in the player's browser; the app never reacts for anyone. A deleted like comment is forgotten and posted again on the next run, starting from zero. Each like comment notifies the Issue's subscribers; after the first deployment the scheduled runs add comments to the existing entries, at most 20 a run and one a second. An entry whose Issue cannot be read or commented on is skipped and reported at the end of the run. A publisher older than likes refuses a `submissions.json` that holds `likes`; remove that key before rolling back.

One account can have at most 40 live (not withdrawn) entries in the library and at most 60 entries of any status (withdrawn entries stay in the snapshot; a maintainer removes them to make room), and it can publish something at most 5 times on one day (by the Issue's update date, UTC): every Issue or edit of an Issue that publishes counts (a withdrawal does not), and the count stays when that Issue is later edited into a body that fails. A submission over either limit fails with a receipt that says so. Withdrawn entries do not count against the library's capacity and leave the snapshot 30 days after their withdrawal. A maintainer can remove an entry with the workflow's `removed` status: the entry is deleted from the snapshot, links to it are dropped and the entries that had them get a new revision. A removed ID is recorded and cannot be published again, from the same Issue or a new one.

Text fields refuse bidirectional controls (U+202A–U+202E, U+2066–U+2069) and the line and paragraph separators (U+2028, U+2029); single-line fields (title, tags, boss, phase, role, game version, source) also refuse zero-width characters (U+200B–U+200D, U+2060, U+FEFF). The rule applies to items an Issue adds or changes; entries published before it stay in the library as published, but current versions of MentorRecorder do not show or import them.

## Publication

`v1/index.json` points to an immutable commit and a SHA-256 for `v1/snapshot.json`. The snapshot bundles items for anonymous downloads, and `v1/reminders/` and `v1/macros/` mirror the entries for review. Hashes validate the downloaded bytes. Verification of gameplay advice requires maintainer review. Formats are defined in [the schema](../schemas/community-content-v1.schema.json).

The workflow detects a structured marker in Issue text even if GitHub omitted the label. It reads the current Issue and authenticates its author from GitHub metadata. Scheduled runs recover missed events. Community jobs queue in their own concurrency group, so edits to open Issues never hold up calibration publishing, and they rebuild from current main when a push loses a race with another writer. GitCode mirroring runs after successful or failed publication jobs finish and on a 30-minute schedule.
